# 4. 명세서 설계와 TDD 방식으로 개발 시작하기

## 1) 데이터 설계
데이터 모델은 프로젝트의 기초 골격이다. 테이블 구조가 잘못되면 API도, 컴포넌트도, 테스트도 전부 틀어진다. 특히 AI와 작업할 때 데이터 모델이 명확하지 않으면, 클로드 코드가 필드명을 제멋대로 정하거나 없는 컬럼을 참조하는 코드를 생성하게 된다.

### DATA_MODEL.md에 포함해야 할 것
데이터 모델 문서는 엔티티와 필드 정의, 테이블 연관관계, 비즈니스 규칙과 제약 조건을 정의한다. 초기 버전의 Tika 앱 프로젝트에서는 연관관계가 별도로 없기 때문에 핵심 테이블인 tickets entity를 다음과 같이 설계해주면 된다.

### tickets entity 설계

| 컬럼 | 타입 | 제약 조건 | 기본값 | 설명 |
|---|---|---|---|---|
| **id** | SERIAL | PK, auto-increment | — | 티켓 고유 식별자 |
| **title** | VARCHAR(200) | NOT NULL | — | 티켓 제목 |
| **description** | TEXT | NULLABLE | NULL | 티켓 상세 설명 |
| **status** | VARCHAR(20) | NOT NULL | 'BACKLOG' | 현재 상태(컬럼) |
| **priority** | VARCHAR(10) | NOT NULL | 'MEDIUM' | 우선순위 |
| **position** | INTEGER | NOT NULL | 1 | 컬럼 내 표시 순서 |
| **planned_start_date** | DATE | NULLABLE | NULL | 시작예정일(사용자 입력) |
| **due_date** | DATE | NULLABLE | NULL | 종료예정일(사용자 입력) |
| **started_at** | TIMESTAMP | NULLABLE | NULL | 시작일(TODO 이동 시 자동) |
| **completed_at** | TIMESTAMP | NULLABLE | NULL | 종료일(Done 이동 시 자동) |
| **created_at** | TIMESTAMP | NOT NULL | now() | 생성 시각 |
| **updated_at** | TIMESTAMP | NOT NULL | now() | 수정 시각 |

> 이 엔티티에 적용되는 비즈니스 규칙은 데이터 저장/수정 시 명시한다. 이 규칙이 없으면 클로드 코드가 "완료 상태로 이동할 때 completedAt을 기록할까요?"처럼 개발자에게 되물어야 하는 상황이 생긴다.


## 2) API 설계
API 명세는 프런트엔드와 백엔드 사이의 계약Contract이다. 프런트엔드 개발자(또는 프런트엔드를 구현하는 AI)는 이 명세만 보고 API를 호출하는 코드를 작성할 수 있어야 하고, 백엔드 개발자(또는 백엔드를 구현하는 AI)는 이 명세대로 정확히 동작하는 API를 만들어야 한다.

### API_SPEC.md의 구조
Tika의 API는 티켓 CRUD와 상태/순서 변경, 총 8개 엔드포인트로 구성된다. 앞절에서 이미 정의한 바 있다.   
클로드 코드에게 Requirements에 있는 FR 문서를 살펴보고 DATA MODEL.md를 참고해서 URL과 HTTP API 스펙을 그대로 작성해달라고 요청한 뒤 응답에대한 값만 정의해주면 API_SPEC.md 문서는 완성이 될 것이다. 개발자는 다음과 같은 스펙에 대한 필드가 제대로 되었는지 검증만 해보면 된다.

### POST /api/tickets — 티켓 생성

| 필드 | 타입 | 필수 | 제약 조건 |
|---|---|---|---|
| **title** | string | O | 1~200자 |
| **description** | string | X | 최대 1000자 |
| **priority** | string | X | LOW \| MEDIUM \| HIGH, 기본값 MEDIUM |
| **plannedStartDate** | string | X | YYYY-MM-DD |
| **dueDate** | string | X | YYYY-MM-DD |

## 코드별 에러 메시지

| 상태 코드 | 조건 | 에러 메시지 |
|---|---|---|
| **400** | title 누락 | 제목을 입력해주세요 |
| **400** | title 200자 초과 | 제목은 200자 이내로 입력해주세요 |
| **400** | 과거 종료예정일 | 종료예정일은 오늘 이후여야 합니다 |
| **400** | 잘못된 priority 값 | 우선순위는 LOW, MEDIUM, HIGH 중 하나여야 합니다 |

### 공통 규칙 정의

개별 엔드포인트 명세 외에 모든 API에 적용되는 공통 규칙도 문서 상단에 정리한다.

- **에러 응답 형식**: 모든 에러는 동일한 구조를 따른다.

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "제목을 입력해주세요"
  }
}
```

- **상태 코드 규칙**: 200(조회/수정 성공), 201(생성 성공), 204(삭제 성공), 400(검증 패), 404(리소스 없음), 500(서버 오류)의 형태로 일반적인 RESTFul 형식의 에러 코드를 따른다. 물론 응답 바디에 HTTP 상태 코드를 함께 포함하거나, 시스템 내부 전용 에러 코드 체계를 별도로 정의하는 등 더 정교한 방식으로 처리해도 무방하다. 여기서는 작은 기능의 MVP이므로 빠르게 완성하는 것을 목표로 하기 때문에 이 정도 응답 형태도 충분할 것이다.

## 3) 컴포넌트 및 UseCase 설계

프론트엔드 개발에서는 UI 컴포트의 명세도 중요하다. 컴포넌트의 책임, 입/출력, 상태를 정의한다. 클로드 코드에게 작업 요청을 했을 때 AI가 이 명세들을 바탕으로 Props와 상태 관리, 하위 컴포넌트 구조 등을 작성하므로 가급적 스펙을 정의하는 것이 좋다. 클로드 코드에게 PRD, TRD, DATA_MODEL, API_SPEC을 기반으로 COMPONENT_SPEC.md를 정의해 달라고 요청한 뒤 상세 내용은 검토를 하며 수정해나가야 한다.

```
    └── TicketModal (상세/수정 모달)

        └── DeleteButton ── ConfirmDialog
```

### 레이아웃 구성 (PRD 기준)

...중략...

- **Backlog**: 좌측 사이드바 (별도 스크롤)
- **TODO / In Progress / Done**: 우측 메인 영역 3컬럼 그리드
- **FilterBar**: 우측 메인 영역 상단에 배치

---

**핵심 동작**:
1. `useTickets` Hook으로 티켓 CRUD 및 DnD 상태 관리
2. DndContext의 `onDragStart`, `onDragOver`, `onDragEnd` 핸들링
3. 드래그 완료 시 대상 컬럼에 따라 API 분기:
   - Done 컬럼 → `useTickets.complete()` → `PATCH /api/tickets/:id/complete`
   - 그 외 컬럼 → `useTickets.reorder()` → `PATCH /api/tickets/reorder`
4. 낙관적 업데이트: UI 즉시 반영 → API 호출 → 실패 시 롤백
