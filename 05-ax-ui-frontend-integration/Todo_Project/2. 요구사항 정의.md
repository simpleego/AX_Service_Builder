## 기능 요구사항 정의(Functional Requirements)

(FR)은 시스템이 무엇을 해야 하는가를 정의한다.   
- "사용자가할 일을 추가할 수 있다"처럼 시스템이 반드시 수행해야 하는 동작을 구체적으로 나열하는 것이다.   
- 기술 스택 선정과 요구사항 정의가 선행되어야 나머지 설계와 구현 단계에서 흔들림 없이 진행할 수 있다.  
- 무엇을 만들지 명확하지 않은 상태에서 코드를 작성하면 방향이 틀어지거나 중간에 설계를 뒤엎는 상황이 생기기 때문이다.

| ID | 기능 | 설명 | API 엔드포인트 |
|---|---|---|---|
| FR-001 | 티켓 생성 | 새 티켓(할 일)을 만들어 Backlog에 추가 | `POST /api/tickets` |
| FR-002 | 목록 조회 | 컬럼별 그룹화된 전체 티켓 조회 | `GET /api/tickets` |
| FR-003 | 상세 조회 | 특정 티켓 전체 정보 + `isOverdue` | `GET /api/tickets/:id` |
| FR-004 | 티켓 수정 | 제목/설명/우선순위/마감일 부분 수정 | `PATCH /api/tickets/:id` |
| FR-005 | 티켓 완료 | Done 영역으로 이동 시 티켓 Soft 삭제 | `PATCH /api/tickets/:id/complete` |
| FR-006 | 티켓 삭제 | 삭제 버튼 클릭 시 혹은 Done으로 상태 변경 이후 24시간이 지나면 영구 삭제 | `DELETE /api/tickets/:id` |
| FR-007 | 상태 이동 | 드래그 앤 드롭(DnD)으로 컬럼/순서 변경 | `PATCH /api/tickets/reorder` |
| FR-008 | 일정초과 | 마감 초과 티켓에 경고 표시 | 조회 시 필드 값으로 구분 |

## 비기능 요구사항 정의
> 비기능 요구사항(Non-Functional Requirements, NFR)은 소프트웨어 개발에서 시스템의 **품질 속성**을 정의하는 제약 조건이다.  
FR은 시스템이 **‘무엇을 해야 하는지’** 를 사용자 관점과 기능 관점에서 명시한다면, NFR은 시스템이 **‘어떻게 수행해야 하는지’** 를 정의한다.  
기술 부채나 성능, 보안 등 기능과는 직접적인 연관은 없지만 사용자에게 제품의 사용성을 위해 추가해야 하는 요구를 말한다.

예를 들어 다음과 같은 항목이 NFR에 해당한다.

- API 응답 시간
- 화면 로딩 속도
- 모바일이나 태블릿에서의 화면 표시 방식
- 성능
- 보안
- 사용성

- ### [표 4-4] 비기능 요구사항 요약

| ID | 항목 | 핵심 기준 |
|---|---|---|
| NFR-001 | 성능 | API 300ms 이하, 화면 로드 2초 이내, 즉각적 드래그 반응 |
| NFR-002 | 반응형 | 모바일(360px) ~ 데스크톱(1920px) |
| NFR-003 | 접근성 | 키보드 네비게이션, 스크린 리더 |
| NFR-004 | **데이터 정합성 보장** | **낙관적 업데이트 + 롤백**, **이중 검증(UI 정합성 보장)** |
| NFR-005 | 브라우저 호환 | Chrome/Safari/Firefox/Edge 최신 2버전 |
| NFR-006 | 배포 | Vercel + Vercel Postgres, HTTPS, Git Push 자동 배포 |

### 데이터 정합성 보장
- 낙관적 업데이트 + 롤백
- 이중 검증(UI 정합성 보장)
`NFR-004 데이터 정합성 보장`은 쉽게 말하면 **화면에 보이는 상태와 서버/DB에 실제 저장된 상태가 서로 어긋나지 않도록 보장하는 요구사항**입니다.

여기에는 두 가지 핵심 개념이 들어 있습니다.

- **낙관적 업데이트 + 롤백**
- **이중 검증(UI 정합성 보장)**

예를 들어 칸반 보드에서 사용자가 티켓을 `Backlog → Done`으로 드래그했다고 가정하겠습니다.

보통 사용자는 드래그하자마자 화면에서 바로 이동된 것을 보고 싶습니다. 서버 응답을 기다렸다가 0.5초 뒤에 움직이면 답답할 수 있습니다. 그래서 프론트엔드에서는 **서버 성공을 먼저 기다리지 않고 화면을 즉시 변경**합니다.

```text
사용자 드래그
   ↓
화면에서 즉시 Done으로 이동
   ↓
서버에 PATCH 요청
   ↓
성공 → 그대로 유지
실패 → 원래 위치로 복구
```

이 방식이 **낙관적 업데이트(Optimistic Update)** 입니다.

예를 들어:

```javascript
// 1. 화면에서는 먼저 이동
moveTicketToDone(id);

// 2. 서버 요청
try {
    await updateTicket(id, "done");
} catch (error) {
    // 3. 실패하면 원래 상태로 되돌림
    moveTicketToBacklog(id);
}
```

여기서 실패했을 때 원래 상태로 되돌리는 것이 **롤백(Rollback)** 입니다.

두 번째인 **이중 검증**은 프론트엔드만 믿지 않고 서버에서도 다시 검사한다는 의미입니다.

예를 들어 사용자가 마감일을 입력할 때:

```text
프론트엔드
마감일 형식 검사
        ↓
API 요청
        ↓
백엔드
마감일 형식 다시 검사
        ↓
DB 저장
```

프론트엔드에서:

```javascript
if (!dueDate) {
    alert("마감일을 입력하세요.");
}
```

라고 검증하더라도 사용자가 API를 직접 호출할 수도 있기 때문에 서버에서도 다시 검증해야 합니다.

FastAPI라면 예를 들어:

```python
from pydantic import BaseModel
from datetime import date

class Ticket(BaseModel):
    title: str
    due_date: date
```

처럼 서버에서 데이터 타입을 다시 검증합니다.

따라서 이 요구사항을 더 쉽게 표현하면 다음과 같습니다.

> **사용자 화면의 상태와 서버 데이터가 항상 일치하도록 하고, 화면을 먼저 변경한 경우 서버 처리 실패 시 이전 상태로 복구한다. 또한 중요한 데이터는 프론트엔드와 백엔드에서 모두 검증한다.**

수업용으로는 표의 문구도 조금 더 명확하게 바꾸는 것을 권합니다.

```markdown
| NFR-004 | 데이터 정합성 | UI와 서버 데이터의 상태 일치 보장, 낙관적 업데이트 실패 시 롤백, 프론트엔드·백엔드 이중 검증 |
```

핵심은 아주 간단합니다.

**“화면에서는 성공한 것처럼 보이는데 DB에는 실패한 상태”를 만들지 않는 것**이 데이터 정합성 보장의 핵심입니다.
