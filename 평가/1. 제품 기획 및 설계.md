#  **AX 프로덕트 기획·서비스 설계
> `Persona → User Journey → Wireframe → Prototype → UT → MVP`
> 그리고 AI 서비스의 `Hallucination`, `Human-in-the-loop`, 성과지표까지 이해했는지를 확인
> 특히 단순 용어 암기뿐 아니라 **쇼핑몰·학교 챗봇 같은 사례에 적용하는 능력**도 준비

## AX 프로덕트 기획&서비스 설계 사전학습 정리

| 핵심 개념             | 학생들이 알아야 할 내용                               | 쉽게 기억하기                       |
| ----------------- | ------------------------------------------- | ----------------------------- |
| 문제 정의             | 서비스를 만들기 전에 **어떤 문제를 누구를 위해 해결할 것인지** 먼저 정의 | `누구의 어떤 문제인가?`                |
| 사용자 조사            | 인터뷰, 설문 등을 통해 사용자의 불편·요구 파악                 | 개발자가 추측하지 말고 사용자에게 물어보기       |
| 기능 요구사항           | 시스템이 **무엇을 해야 하는가**를 정의                     | "주문내역을 조회할 수 있다"              |
| 비기능 요구사항          | 성능·보안·가용성 등 **어떻게 동작해야 하는가**                | "2초 이내", "암호화", "24시간 운영"     |
| Persona           | 대표 사용자의 특징·목표·불편을 설정한 가상의 사용자               | 대표 고객 한 명 만들기                 |
| User Journey      | 사용자가 서비스를 이용하는 과정을 단계별로 정리                  | 회원가입 → 검색 → 주문 → 결제           |
| Wireframe         | 화면의 메뉴·버튼·콘텐츠 배치를 간단히 표현한 설계도               | 화면의 뼈대                        |
| Prototype         | 클릭·화면 이동 등이 가능한 시제품                         | 동작하는 화면 모형                    |
| UT                | 실제 사용자가 프로토타입을 사용하면서 문제점을 찾는 테스트            | User Test                     |
| MVP               | 핵심 기능만 먼저 구현해 시장·사용자 반응을 확인                 | 작게 만들고 빨리 검증                  |
| MoSCoW            | 기능의 중요도를 4단계로 분류                            | Must / Should / Could / Won't |
| Hallucination     | AI가 틀린 내용을 사실처럼 만들어 답하는 현상                  | AI의 그럴듯한 오답                   |
| Human-in-the-loop | 중요한 판단이나 실행 전에 사람이 확인                       | AI 제안 → 사람 검토 → 실행            |
| 성과지표              | 서비스가 실제로 효과가 있는지 측정하는 기준                    | 해결률, 만족도 등                    |

시험 문제에서도 서비스 기획의 출발점을 **문제와 사용자 정의**로 보고 있으며, 사용자 요구 파악에는 인터뷰·설문 같은 사용자 조사가 중요하게 다뤄집니다. 또한 기능 요구사항과 비기능 요구사항을 구분할 수 있어야 합니다. 

### 1. 서비스 기획은 무엇부터 시작하는가?

서비스 기획은 화면 디자인이나 프로그래밍부터 시작하는 것이 아닙니다.

**문제 발견 → 사용자 정의 → 사용자 조사 → 요구사항 정의 → 해결방법 설계**

예를 들어 쇼핑몰을 만든다고 해서 바로 "상품 검색 기능을 만들자"라고 생각하면 안 됩니다.

사용자 문제를 먼저 생각해야 합니다.

> 사용자가 상품 종류가 너무 많아서 자신에게 맞는 상품을 찾기 어렵다.

그다음 사용자를 정합니다.

> 20~30대 온라인 쇼핑 사용자

이제 해결 방법을 생각합니다.

> AI 상품 추천 기능

즉 학생들은 다음 질문을 항상 생각하면 됩니다.

**"누가 → 어떤 불편을 가지고 있고 → 그것을 어떻게 해결할 것인가?"**

---

## 2. 기능 요구사항과 비기능 요구사항

시험에서 매우 중요한 구분입니다.

**기능 요구사항(Functional Requirement)**은 서비스가 제공해야 하는 기능입니다.

예를 들어:

`사용자는 로그인할 수 있어야 한다.`
`사용자는 상품을 검색할 수 있어야 한다.`
`사용자는 주문 내역을 조회할 수 있어야 한다.`

반면 **비기능 요구사항(Non-functional Requirement)**은 기능의 성능이나 품질 조건입니다.

`첫 화면은 2초 이내에 표시되어야 한다.`
`개인정보는 암호화해야 한다.`
`서비스는 24시간 운영되어야 한다.`

따라서 이렇게 구분하면 쉽습니다.

**기능 = 무엇을 할 수 있는가?**

**비기능 = 얼마나 빠르고, 안전하고, 안정적으로 해야 하는가?**

## 3. Persona

Persona는 실제 사람 한 명이 아니라 **대표 사용자를 구체화해서 만든 가상의 사용자 모델**입니다. 시험에서도 사용자의 특성·목표·불편을 구체화하는 용어로 출제됩니다. 

예를 들어 쇼핑몰이라면:

**김초보, 25세, 대학생**

목표: 저렴한 노트북을 구입하고 싶음
불편: 컴퓨터 사양을 잘 모름
행동: 검색과 리뷰를 많이 봄
필요: 쉽게 비교하고 추천받고 싶음

이 Persona를 보고 개발자는

> "사양 비교 AI를 만들면 도움이 되겠다."

와 같은 기능을 생각할 수 있습니다.

따라서

**Persona = 대표 사용자**

라고 기억하면 됩니다.

---

## 4. User Journey

User Journey는 사용자가 서비스를 이용하면서 거치는 과정을 시간 순서대로 표현한 것입니다.

쇼핑몰을 예로 들면:

**회원가입 → 로그인 → 상품검색 → 상품상세 → 장바구니 → 주문 → 결제 → 배송조회**

단순히 화면 순서만 기록하는 것이 아니라 각 단계에서 사용자가 무엇을 생각하고 어떤 불편을 느끼는지도 분석할 수 있습니다.

예를 들어:

`상품 검색 → 검색 결과가 너무 많음 → 선택하기 어려움`

여기서 새로운 AI 기능을 생각할 수 있습니다.

`AI 상품 추천`

따라서 User Journey는 **사용자의 행동과 경험을 이해하기 위한 도구**입니다. 시험에서도 사용자가 회원가입부터 구매까지 거치는 단계를 정리한 것을 User Journey로 묻고 있습니다. 

---

## 5. Wireframe

Wireframe은 실제 화면을 만들기 전에 작성하는 **화면의 뼈대**입니다.

예를 들어 쇼핑몰 화면을 아주 단순하게 표현하면:

```text
┌─────────────────────────┐
│       쇼핑몰 LOGO        │
├─────────────────────────┤
│ 검색어 [            ] 🔍 │
├─────────────────────────┤
│ 카테고리 | 상품 | 이벤트 │
├─────────────────────────┤
│                         │
│       상품 목록          │
│                         │
├─────────────────────────┤
│ 장바구니        구매하기 │
└─────────────────────────┘
```

여기에서는 색상, 예쁜 이미지보다

**어디에 무엇을 배치할 것인가**

를 결정하는 것이 중요합니다.

따라서

**Wireframe = 화면 배치 설계도**

라고 기억하면 됩니다. 

---

## 6. Prototype

Wireframe보다 한 단계 발전된 것이 Prototype입니다.

Wireframe이

> "버튼은 여기에 배치하자."

정도라면,

Prototype은

> "이 버튼을 클릭하면 다음 화면으로 이동한다."

정도까지 구현합니다.

시험에서는 **실제 서비스처럼 화면 이동이나 버튼 클릭을 시험해 볼 수 있는 시제품**을 Prototype으로 정의하고 있습니다. 

관계를 기억하면 쉽습니다.

**Wireframe → 화면 구조**

**Prototype → 화면 동작**

---

## 7. UT(User Test)

Prototype을 만들었다면 실제 사용자에게 사용시켜 봅니다.

예를 들어 쇼핑몰 Prototype을 학생들에게 사용하게 한 후

> "구매 버튼을 찾기 어려웠어요."

> "결제 단계가 너무 복잡해요."

같은 의견을 받습니다.

그리고 UI를 수정합니다.

이 과정을 **UT(User Test)**라고 합니다. 시험에서는 제작한 프로토타입을 실제 사용자가 사용하고 불편·개선점을 찾는 테스트를 영어 약자로 묻습니다. 

---

## 8. MVP

MVP는

**Minimum Viable Product**

즉 **최소 기능 제품**입니다.

처음부터 완벽한 서비스를 만드는 것이 아니라 핵심 기능만 먼저 만들어 사용자 반응을 확인합니다.

예를 들어 AI 쇼핑몰을 만들 때 처음부터

회원관리 + 상품관리 + 주문 + 결제 + 배송 + 리뷰 + 챗봇 + 추천 + 음성검색

을 모두 만들 필요는 없습니다.

처음에는

**상품검색 + AI 추천**

정도만 만들어 볼 수 있습니다.

사용자가 실제로 사용해 보고 반응이 좋다면 기능을 확장합니다.

따라서 핵심은

**작게 개발 → 빠르게 검증 → 개선**

입니다. 시험에서도 MVP를 "핵심 기능만 먼저 만들어 사용자 반응을 빠르게 검증하기 위한 것"으로 다룹니다.

## 9. MoSCoW 우선순위

기능이 너무 많으면 어떤 기능부터 개발할지 결정해야 합니다.

이때 사용할 수 있는 방법이 **MoSCoW**입니다.

```text
Must have
↓
반드시 필요한 기능

Should have
↓
중요하지만 없어도 서비스 가능

Could have
↓
있으면 좋은 기능

Won't have
↓
이번 개발에서는 제외
```

쇼핑몰이라면 예를 들어:

```text
Must     상품조회, 주문
Should   리뷰
Could    AI 상품추천
Won't    AR 가상착용
```

시험에서는 이 네 단계의 기능 우선순위 기법 이름을 직접 묻고 있습니다.

# 10. AI 서비스에서 매우 중요한 Hallucination

AI 서비스에서는 일반 웹서비스와 다른 문제가 있습니다.

LLM이 자신이 알지 못하는 내용을 **그럴듯하게 만들어서 답할 수 있습니다.**

이를

**Hallucination(할루시네이션)**

이라고 합니다. 시험에서 객관식과 단답형으로 반복 출제되고 있으므로 반드시 기억해야 합니다. 

예를 들어 학교 챗봇에게

> "2026년 장학금 신청 마감일이 언제야?"

라고 질문했는데 실제 자료에는 없는 날짜를 AI가

> "9월 30일입니다."

라고 만들어냈다면 Hallucination입니다.

---

# 11. Hallucination 대책

AI 서비스를 기획할 때는 단순히

**"AI가 알아서 잘 대답한다."**

라고 설계하면 안 됩니다.

학교 안내 AI 챗봇이라면 다음과 같은 방식으로 안전성을 높일 수 있습니다.

```text
학교 공식 자료를 근거로 답변
        ↓
답변의 출처 표시
        ↓
확실하지 않으면 모른다고 답변
        ↓
중요한 내용은 담당자 확인
```

특히 장학금, 입학, 등록금처럼 중요한 정보라면

**"정확한 사항은 담당 부서에 확인하세요."**

와 같은 안내가 필요합니다.

시험의 서술형에서도 학교 안내 AI 챗봇에서 잘못된 답변에 대비한 대책을 두 가지 이상 요구합니다. 

---

# 12. Human-in-the-loop

AI가 모든 것을 자동으로 결정하게 하지 않고 **중요한 단계에서 사람이 검토하고 승인하는 방식**입니다.

```text
사용자 요청
   ↓
AI 분석
   ↓
AI 결과 생성
   ↓
사람 확인
   ↓
최종 실행
```

예를 들어:

```text
AI가 대출 심사 자료 분석
        ↓
AI가 의견 제시
        ↓
직원이 검토
        ↓
최종 결정
```

이를

**Human-in-the-loop**

라고 합니다. 

학생들에게는

**AI가 판단하고 → 사람이 확인한다**

라고 기억시키면 쉽습니다.

---

# 13. AI 서비스 성공 여부는 무엇으로 판단하는가?

프로그램이 정상적으로 실행된다고 좋은 서비스는 아닙니다.

실제 사용자의 문제가 해결되었는지를 측정해야 합니다.

예를 들어 AI 상담 서비스라면:

```text
문의 해결률
고객 만족도
응답 시간
재사용률
상담원 연결 감소율
```

등을 측정할 수 있습니다.

시험에서도 AI 상담 서비스의 성과지표로 **사용자 문의 해결률과 만족도**를 제시하고 있습니다. 

---

# 14. 전체 흐름을 하나로 연결해서 기억하기

학생들이 가장 중요하게 공부해야 하는 부분입니다.

```text
① 문제 발견
        ↓
② 사용자 조사
   인터뷰 / 설문
        ↓
③ Persona
   대표 사용자 정의
        ↓
④ User Journey
   사용자 행동 분석
        ↓
⑤ 요구사항 정의
   기능 / 비기능
        ↓
⑥ 기능 우선순위
   MoSCoW
        ↓
⑦ Wireframe
   화면 구조 설계
        ↓
⑧ Prototype
   클릭 가능한 시제품
        ↓
⑨ UT
   실제 사용자 테스트
        ↓
⑩ MVP 개발
   핵심 기능 우선 구현
        ↓
⑪ 서비스 운영
        ↓
⑫ 성과 측정
   해결률 / 만족도 등
```

AI 서비스라면 여기에 추가적으로

```text
Hallucination 관리
Human-in-the-loop
출처 제시
사람의 최종 검토
```

등을 고려해야 합니다.

# 15. 서술형 시험 대비 방법

이번 시험에서는 단순 용어 외에도 **AI 서비스 기획안을 짧게 작성하는 문제**가 포함되어 있습니다. 특히 `사용자 문제 → 대상 사용자 → AI 기능 → 기대 효과 → 검증 방법`의 구조를 이해하는 것이 중요합니다. 

예를 들어 다음 정도의 구조를 익혀 두면 좋습니다.

**사용자 문제**

쇼핑몰에 상품이 너무 많아서 자신에게 적합한 상품을 찾기 어렵다.

↓

**대상 사용자**

상품 선택에 어려움을 느끼는 온라인 쇼핑 사용자

↓

**AI 기능**

사용자의 관심 상품과 구매 이력을 분석하여 상품을 추천한다.

↓

**기대 효과**

상품 검색 시간을 줄이고 구매 편의성을 높인다.

↓

**검증 방법**

AI 추천 상품의 클릭률, 구매전환율, 사용자 만족도를 측정한다.

핵심은 멋진 AI 기술 이름을 쓰는 것이 아니라,

**문제 → 사용자 → 해결 방법 → 효과 → 검증**

의 논리적 연결입니다.

---

## 시험 직전 이것만은 반드시 기억

```text
Persona          = 대표 사용자
User Journey     = 사용자 경험 과정
Wireframe        = 화면 뼈대
Prototype        = 동작 가능한 시제품
UT               = 사용자 테스트
MVP              = 최소 기능 제품
MoSCoW           = 기능 우선순위
Hallucination    = AI의 그럴듯한 잘못된 답변
Human-in-the-loop = AI 결과를 사람이 확인
```

그리고 전체 시험의 핵심 문장을 하나로 정리하면 다음과 같습니다.

> **"사용자의 문제를 먼저 찾고 → 사용자를 이해하고 → 필요한 기능을 설계하고 → 작게 만들어 실제 사용자에게 검증한 뒤 → AI의 오류와 위험을 관리하면서 서비스를 개선한다."**

이 문장을 이해하고 있다면 **1~20번의 객관식·단답형·서술형을 각각 따로 암기하기보다 전체 개념의 연결관계를 이해하면서 시험을 준비할 수 있습니다.**
