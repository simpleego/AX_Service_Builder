# 기차예매
>  최신 LangGraph에서는 `langgraph.prebuilt.create_react_agent()`가 deprecated 상태이고, 일반적인 ReAct 에이전트는 `langchain.agents.create_agent()` 사용이 권장됩니다.
>  LangGraph 자체는 상태 관리, Human-in-the-loop, 장기 실행 workflow를 구성할 때 사용하면 좋습니다. :chatgpt-content-reference{index="0"}
>  또 현재 코레일은 **코레일+**에서 KTX·SRT를 통합 검색·예매하도록 변경되었고, 공식 공개 API에서는 열차 운행계획/운행정보 같은 데이터 조회 기능을 확인할 수 있습니다.
> 제가 확인한 공개 API 범위에서는 일반 사용자의 실제 좌석 예약·결제를 수행하는 공개 API는 확인되지 않았습니다. 따라서 교육용 버전에서는 실제 예약 API를 임의로 호출하지 않고,  
> **열차 검색 Tool을 모의 구현(Mock)** 한 뒤 최종 예매는 사용자 승인을 받도록 설계하겠습니다. :chatgpt-content-reference{index="1"}

## 1. 전체 구조

```text
사용자
  │
  │ "이번 주말 대전↔광주송정,
  │  창가석·순방향으로 찾아줘"
  ▼
┌──────────────────────┐
│ 여행 예약 Agent      │
│ LangChain/LangGraph  │
└──────────┬───────────┘
           │
     ┌─────┴──────────┐
     │                │
     ▼                ▼
[일정 확인 Tool]   [열차 조회 Tool]
                     │
                     ▼
               열차 후보 목록
                     │
                     ▼
               [좌석 평가 Tool]
                     │
                     ▼
            선호도 점수 계산
                     │
                     ▼
            최적 열차/좌석 선택
                     │
                     ▼
           ┌─────────────────┐
           │ Human Approval  │
           │ "예매할까요?"   │
           └───────┬─────────┘
                   │
             사용자 승인
                   ▼
           코레일+ 예매 단계
```

여기서 중요한 부분은 **LLM이 모든 일을 직접 하는 것이 아니라 각각의 기능을 Tool로 만들어 주는 것**입니다.

예를 들어 에이전트에게 다음 4개 Tool을 줄 수 있습니다.

```text
search_train()
        열차 조회

check_seat()
        좌석 확인

score_train()
        내 선호도 평가

request_booking()
        예매 요청
```

이 구조가 바로 앞서 설명한 ReAct의 핵심입니다.

# 6. 좌석 확인 Tool

같은 `tools.py`에 추가합니다.

```python
@tool
def check_seat(train_no: str) -> dict:
    """
    특정 열차의 좌석 상태를 조회한다.
    """

    seats = {

        "KTX503": {
            "window": True,
            "aisle": True,
            "forward": True
        },

        "KTX505": {
            "window": False,
            "aisle": True,
            "forward": True
        },

        "KTX507": {
            "window": True,
            "aisle": True,
            "forward": False
        }
    }

    return seats.get(
        train_no,
        {
            "window": False,
            "aisle": False,
            "forward": False
        }
    )
```

# 7. 좌석 선호도 평가 Tool

여기서 재미있는 부분이 나옵니다.

사용자의 조건에 따라 점수를 계산합니다.

```python
@tool
def score_train(
    departure_time: str,
    window: bool,
    forward: bool
) -> int:
    """
    사용자의 좌석 및 시간 선호도를 이용해
    열차에 점수를 부여한다.
    """

    score = 0

    # 창가 좌석
    if window:
        score += 40

    # 순방향
    if forward:
        score += 30

    # 선호 시간
    if "08:00" <= departure_time <= "10:00":
        score += 30

    return score
```

따라서

```text
KTX503

창가     +40
순방향   +30
시간     +30
----------------
총점     100점
```

처럼 계산할 수 있습니다.

# 8. 예매 요청 Tool

여기서는 **절대로 바로 결제하지 않습니다.**

```python
@tool
def request_booking(

    departure: str,
    arrival: str,
    departure_time: str

실제 예매를 진행하려면
사용자의 최종 승인이 필요합니다.
"""
```

이 부분이 매우 중요합니다.

에이전트 구조에서는 이를 보통

**Human-in-the-loop**

라고 합니다.

# 9. ReAct Agent 생성

`main.py`

```python
from dotenv import load_dotenv

from langchain.agents import create_agent
from langchain_openai import ChatOpenAI

from tools import (
    search_train,
    check_seat,
    score_train,
    request_booking
)

load_dotenv()


model = ChatOpenAI(
    model="gpt-5.6",
    temperature=0
)


tools = [

    search_train,

    check_seat,

    score_train,

    request_booking

]


SYSTEM_PROMPT = """
당신은 기차 여행 예약 도우미입니다.

사용자의 요청을 분석해서 적절한 도구를 사용하십시오.

사용자의 기본 선호조건은 다음과 같습니다.

출발역: 대전
도착역: 광주송정

좌석 우선순위:

1. 창가석
2. 순방향
3. 일반실

열차를 검색한 뒤
각 열차의 좌석을 확인하십시오.

조건에 가장 적합한 열차를 선택하십시오.

실제 예약이나 결제는 절대로 자동 실행하지 마십시오.

최종 단계에서는 반드시
사용자에게 예약 승인을 요청하십시오.
"""


agent = create_agent(

    model=model,

    tools=tools,

    system_prompt=SYSTEM_PROMPT

)
```

최신 LangChain 문서에서는 이처럼 `create_agent()`가 표준적인 agent factory입니다. 내부적으로 tool-call loop를 구성하며, 세밀한 graph 제어가 필요할 때 LangGraph를 추가하는 방식입니다. :chatgpt-content-reference{index="2"}

# 11. Agent 내부에서는 어떤 일이 일어나는가

여기가 교육적으로 가장 중요합니다.

사용자는 단순히

```text
이번 주 토요일
대전 → 광주송정
8~10시
창가석 + 순방향
```

이라고 했습니다.

그러면 Agent가 판단합니다.

```text
사용자 요청
    ↓

열차를 먼저 알아야겠다
    ↓

search_train()

    ↓

KTX503
KTX505
KTX507

    ↓

좌석을 확인해야겠다
```

Agent가 다시 Tool을 호출합니다.

```text
check_seat("KTX503")

check_seat("KTX505")

check_seat("KTX507")
```

결과:

```text
KTX503
창가 O
순방향 O

KTX505
창가 X
순방향 O

KTX507
창가 O
순방향 X
```

다음으로 판단합니다.

```text
score_train()
```

결과:

```text
KTX503 → 100

KTX505 → 60

KTX507 → 70
```

따라서

```text
KTX503
```

을 추천합니다.

# 12. 이것이 바로 ReAct

구조를 단순화하면 다음입니다.

```text
Reason
 ↓
Action
 ↓
Observation
 ↓
Reason
 ↓
Action
 ↓
Observation
 ↓
...
 ↓
Answer
```

기차 예매에 적용하면:

```text
생각
"열차부터 검색해야겠다"

        ↓

Action
search_train()

        ↓

Observation
KTX503
KTX505
KTX507

        ↓

생각
"좌석을 확인해야겠다"

        ↓

Action
check_seat()

        ↓

Observation
창가/순방향 정보

        ↓

생각
"선호도를 평가해야겠다"

        ↓

Action
score_train()

        ↓

Observation
100 / 60 / 70

        ↓

판단

KTX503 선택
```

즉 앞서 질문하셨던

> ReAct 기술도 결국 누군가 프로그래밍해야 하는가?

에 대한 아주 좋은 답이 됩니다.

**그렇습니다.**

다만 프로그래머가

```python
if 조건:
    함수1()

if 조건:
    함수2()

if 조건:
    함수3()
```

처럼 모든 실행 순서를 결정하지 않습니다.

프로그래머는 주로 **Tool을 만들어 줍니다.**

```text
프로그래머

search_train()
check_seat()
score_train()
request_booking()
```

그리고

```text
어떤 Tool을
어떤 순서로
몇 번 사용할 것인가?
```

를 상당 부분 **Agent가 판단**합니다.

# 13. 일반 프로그램과 Agent의 결정적인 차이

일반 프로그램은:

```python
trains = search_train()

for train in trains:

    seat = check_seat()

    score = score_train()

best = max(...)

booking(best)
```

개발자가 순서를 결정합니다.

반면 Agent는:

```text
LLM

   ↓ 판단

search_train()

   ↓ 판단

check_seat()

   ↓ 판단

check_seat()

   ↓ 판단

score_train()

   ↓ 판단

request_booking()
```

입니다.

그래서 Agent의 핵심은

> **Workflow를 전부 코드로 고정하지 않는다.**

라고 볼 수 있습니다.

## 14. 하지만 실전에서는 LangGraph를 섞는 것이 좋습니다

기차 예매처럼 돈이 관련된 작업은 **완전 자유형 ReAct Agent**로 만드는 것보다는 다음처럼 제어하는 것이 좋습니다.

```text
                ┌─────────────┐
                │ 사용자 요청 │
                └──────┬──────┘
                       ↓
                ┌─────────────┐
                │ ReAct Agent │
                │ 여행 분석   │
                └──────┬──────┘
                       ↓
              ┌──────────────────┐
              │ 열차/좌석 검색  │
              └───────┬──────────┘
                      ↓
              ┌──────────────────┐
              │ 후보 평가       │
              └───────┬──────────┘
                      ↓
              ┌──────────────────┐
              │ LangGraph        │
              │ Human Approval   │
              └───────┬──────────┘
                      ↓
                 승인 / 거절
                   ↙     ↘
               승인       거절
                ↓          ↓
             예약단계      종료
```

즉,

**판단은 Agent에게 맡기고, 중요한 절차는 Graph로 통제합니다.**

이게 실제 서비스에서는 훨씬 좋은 설계입니다.

## 15. 최종적으로 발전시키면

이 교육 예제를 조금씩 확장하면 상당히 실용적인 Agent가 됩니다.

```text
[Google Calendar]
       ↓
주말 일정 확인
       ↓
[Train Agent]
       ↓
대전 → 광주송정 검색
       ↓
시간 조건
       ↓
좌석 조건
       ↓
가격 비교
       ↓
후보 3개
       ↓
LLM 판단
       ↓
최적 후보
       ↓
사용자 승인
       ↓
코레일+
       ↓
예약 완료
       ↓
[Gmail]
       ↓
승차권 확인
       ↓
[Calendar]
       ↓
여행 일정 등록
```

이 정도가 되면 단순 챗봇이 아니라 **Personal Travel Agent**에 가까워집니다.

특히 교육용으로는 이 예제가 좋습니다. 학생들이 `LLM → Tool Calling → ReAct → State → Human-in-the-loop → Agent 자동화`가 왜 필요한지를 기차 예매라는 친숙한 사례 하나로 연결해서 이해할 수 있기 때문입니다. :chatgpt-content-reference{index="3"}

현재 코레일 공개 API에는 실제 운행계획·운행정보 조회 기능이 있으므로, **2차 버전에서는 Mock 데이터를 제거하고 공식 열차 운행정보 API와 연결하는 실습**으로 발전시키고, **3차 버전에서는 LangGraph의 StateGraph와 interrupt를 사용해 진짜 Human-in-the-loop 구조**로 만드는 순서가 가장 적절합니다. :chatgpt-content-reference{index="4"}
