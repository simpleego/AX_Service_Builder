# SDD 개발 방식에서 개발자와 AI의 역할 분담

SDD(Specification-Driven Development, 명세 기반 개발)에서 가장 중요한 원칙은 개발자는 무엇을 왜 만들어야 하는지 결정하고, AI는 명세를 기반으로 어떻게 구현할지 제안하고 실행하며, 개발자는 결과를 검증하고 승인한다는 것입니다.

기존 개발에서는 개발자가 설계부터 코딩까지 대부분 직접 수행했다면, AI 기반 SDD에서는 개발자의 역할이 직접 구현 중심에서 요구사항 정의·설계 의사결정·검증·품질 책임 중심으로 이동합니다.

단, 개발자가 모든 명세서를 직접 작성하거나 AI가 모든 코드를 자동으로 생성해야 한다는 뜻은 아닙니다. AI가 명세 초안을 작성하고 개발자가 이를 검토·확정하는 방식이 현실적입니다.

## 1. 개발 단계별 역할 비교

| 개발 단계     | 개발자(Human)              | AI                      |
| --------- | ----------------------- | ----------------------- |
| ① 문제 정의   | 해결할 문제, 목적, 사용자 결정      | 아이디어 분석, 문제점 및 대안 제시    |
| ② 요구사항 분석 | 기능 범위, 우선순위, 제약조건 확정    | 요구사항 초안, 누락 사항 분석       |
| ③ 명세서 작성  | 업무 규칙, 성공 기준 검토·승인      | 기능/API/DB/테스트 명세 초안 생성  |
| ④ 아키텍처 설계 | 기술 선택, 구조 및 보안 정책 결정    | 아키텍처 대안, 설계도, ERD 생성    |
| ⑤ 작업 계획   | 구현 순서, 작업 단위, 승인 기준 결정  | 작업 분해, 의존성 분석, 일정 제안    |
| ⑥ 코드 구현   | 핵심 로직 검토, 복잡한 문제 해결     | FE/BE/DB 코드 생성 및 수정     |
| ⑦ 테스트     | 검증 기준 확정, 핵심 결과 확인      | 단위·통합·E2E 테스트 작성·실행     |
| ⑧ 코드 리뷰   | 품질·보안·유지보수성 최종 판단       | 코드 분석, 버그 탐지, 개선안 제시    |
| ⑨ 배포      | 배포 정책 승인, 운영 위험 판단      | CI/CD 구성, 배포 자동화, 로그 분석 |
| ⑩ 유지보수    | 변경사항 승인, 장애 책임과 우선순위 결정 | 오류 원인 분석, 수정 코드 생성      |

핵심: 개발자는 의사결정과 최종 책임을 담당하고, AI는 문서화·구현·분석·반복 작업을 가속합니다.

다만 AI 에이전트의 자율 실행 범위는 프로젝트 위험도에 따라 조정해야 합니다. 예를 들어 테스트 실행은 AI에 맡기더라도 운영 DB 삭제나 실제 서비스 배포는 별도 승인을 요구하는 것이 안전합니다.

## 2. SDD에서 가장 중요한 개발 프로세스와 승인 지점

실제 프로젝트에서는 AI가 각 단계의 결과물을 생성하고 개발자가 검토한 뒤 다음 단계로 진행하는 Human-in-the-Loop 방식을 권장합니다.

개발자: 목표·요구사항·제약조건 결정

AI: 명세서·설계서·작업 계획 생성

개발자: 설계·명세 검토 및 승인

AI: 코드·테스트 생성 및 실행

개발자: 실행 결과·품질·보안 검증

최종 승인 → 배포 → 개선 반복

이러한 흐름은 GitHub의 Spec Kit에서도 확인할 수 있습니다. 공식 워크플로는 명세 작성(Specify) → 기술 계획(Plan) → 작업 분해(Tasks) → 구현(Implement) → 명세 대비 완성도 확인(Converge)을 기본으로 하며, 필요에 따라 명세 명확화와 일관성 검사를 추가합니다.&#x20;

## 3. 명세서별 개발자와 AI의 책임

SDD 교육에서는 명세서마다 누가 초안을 만들고 누가 확정하는지 구분하는 것이 중요합니다.

| 명세서               | AI가 수행할 업무       | 개발자가 반드시 확인할 내용   |
| ----------------- | ---------------- | ----------------- |
| `requirements.md` | 요구사항·사용자 스토리 작성  | 실제 사용자 요구, 기능 범위  |
| `architecture.md` | 시스템 구조·기술 대안 작성  | 아키텍처 타당성, 기술 선택   |
| `database.md`     | ERD, 테이블·관계 설계   | 데이터 무결성, 정규화, 보안  |
| `api-spec.yaml`   | OpenAPI 규격 초안 작성 | API 동작, 인증, 오류 정책 |
| `ui-spec.md`      | 화면 흐름·컴포넌트 정의    | 사용성, 접근성, 화면 요구사항 |
| `tasks.md`        | 개발 작업 분할·순서 생성   | 우선순위, 의존성, 범위     |
| `test-spec.md`    | 테스트 시나리오·케이스 생성  | 정상·예외·경계 조건의 적절성  |

위 문서들은 교육용 권장 예시이며, 모든 SDD 도구가 이 파일 이름이나 구성을 요구하는 것은 아닙니다.

## 4. 실제 개발 예시: Todo 앱

목표: React + FastAPI + DB를 활용하여 할 일 관리 서비스를 SDD로 개발

1단계 — 개발자가 요구사항을 정의

사용자는 할 일을 추가·조회·완료·삭제할 수 있어야 한다. 제목은 1\~100자이며, 새로고침해도 데이터가 유지되어야 한다. 로그인은 구현하지 않는다.

2단계 — AI가 설계와 명세서를 작성

요구사항 문서, API 설계, DB 스키마, React 컴포넌트 구성, 작업 계획 등을 생성한다.

3단계 — 개발자가 기술적인 내용을 검토

REST API가 적절한지, 테이블 구조가 타당한지, 예외 처리가 충분한지, 기능이 요구사항을 충족하는지 판단한다.

4단계 — AI가 구현 및 테스트

React 화면, FastAPI 라우터, 데이터 저장 기능, pytest 테스트를 구현하고 실행한다.

5단계 — 개발자가 최종 검증

Postman에서 API를 확인하고, 브라우저에서 실제 사용 시나리오를 검증한다. 문제 발견 시 명세와 구현 중 어느 부분을 수정할지 결정한다.

## 5. AI 시대에 개발자가 반드시 갖추어야 할 역량

여기서 중요한 문제가 하나 있습니다.

AI가 명세서도 작성하고 코드도 생성한다면, 개발자가 기술적인 내용을 몰라도 되는가?

그렇지는 않습니다. 개발자는 모든 코드를 직접 작성할 필요는 줄어들 수 있지만, AI 결과가 적절한지 판단하는 기술적 역량은 여전히 필요합니다.

특히 비전공자 교육에서는 다음 다섯 가지를 반드시 학습해야 합니다.

- 요구사항 분석 능력: 무엇을 만들고, 어떤 조건에서 정상 동작해야 하는지 정의
- 아키텍처 이해 능력: FE·BE·DB·API 사이의 데이터 흐름 파악
- 코드 이해 능력: AI가 생성한 핵심 로직을 읽고 오류를 발견
- 테스트 및 디버깅 능력: 정상·비정상 상황을 검증하고 실패 원인 분석
- AI 작업 통제 능력: 명세 제공, 실행 범위 제한, 결과 검토, 수정 요청

## 6. 결론: 개발자와 AI의 이상적인 역할

개발자

## 판단과 책임

요구사항 확정, 기술적 판단, 설계 승인, 품질 검증, 최종 의사결정

AI

## 생성과 실행

명세 초안, 설계 대안, 코드 생성, 테스트 자동화, 오류 분석, 반복 수정

따라서 SDD 기반 개발자 교육은 단순히 AI에게 코드를 생성시키는 교육이 되어서는 안 됩니다.

개발자가 요구사항과 시스템 구조를 이해하고, AI가 만든 명세·설계·코드의 타당성을 판단하고 검증할 수 있도록 하는 교육이 핵심입니다.

이는 앞서 논의한 ① 직접 개발 → ② AI 협업 개발 → ③ AI 에이전트 기반 SDD 개발의 단계적 학습 방식과도 잘 연결됩니다.&#x20;
