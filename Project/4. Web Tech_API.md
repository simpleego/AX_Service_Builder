# 주요 기술 시대별 종류별 정리

## 1. 요청-응답형 API

### SOAP (Simple Object Access Protocol)
<img width="1055" height="1491" alt="image" src="https://github.com/user-attachments/assets/378fc08c-3aa0-4631-b1f5-11102ae7659d" />

- **배경과 시기**: 1998년 Microsoft 주도로 설계되었고, 2000년 SOAP 1.1, 2003년 SOAP 1.2가 W3C 표준이 되었습니다. 당시 분산 객체 기술인 CORBA와 DCOM은 너무 복잡했고, HTTP가 이미 널리 쓰이고 있었습니다. SOAP은 HTTP(또는 다른 프로토콜)로 XML 기반 메시지를 주고받는 방식을 표준화했습니다. 2010년대부터는 REST에 밀렸지만, 여전히 금융·공공기관 등에서 생존 중입니다.
- **장점**: WSDL로 인터페이스를 엄격히 정의하고, WS-Security·트랜잭션·신뢰성 전송 같은 엔터프라이즈 기능이 표준화되어 있습니다. 전송 프로토콜에도 무관합니다.
- **단점**: XML이 장황해서 메시지가 무겁고 파싱이 느립니다. 스펙이 방대해 학습과 구현 부담이 크고, 브라우저나 모바일 환경과 잘 맞지 않습니다.
- **응용분야**: 은행·보험 등 금융 시스템, 공공기관 연계, 통신사 과금 시스템, 오래된 ERP 연동(레거시 유지보수 영역)

### REST (Representational State Transfer)

<img width="1055" height="1491" alt="image" src="https://github.com/user-attachments/assets/7e6849f7-90ac-4b2e-b4f2-8017b9662a79" />

- **배경과 시기**: 2000년 HTTP 설계자 중 한 명인 Roy Fielding이 박사 논문에서 제안했습니다. "웹이 이렇게 크게 확장될 수 있었던 원리"를 아키텍처 스타일로 추상화한 것이 REST입니다. 2010년대 스마트폰과 Open API 확산에 딱 맞아떨어져 표준이 되었습니다. 지금도 가장 널리 쓰입니다.
- **장점**: URL(자원)과 HTTP 메서드(행위)라는 단순한 모델이라 이해하기 쉽습니다. 무상태(stateless)라 서버 확장이 쉽고, HTTP 캐싱을 그대로 활용할 수 있어 성능이 좋습니다. 기존 웹 인프라를 그대로 쓸 수 있습니다.
- **단점**: 필요 이상의 데이터를 받거나(over-fetching) 화면 하나에 여러 번 호출해야 하는(under-fetching) 문제가 있습니다. 엄격한 스펙이 없어 팀마다 설계가 들쭉날쭉합니다.
- **응용분야**: 웹/모바일 백엔드 API, 공개 Open API(공공데이터포털, 지도·결제 API), SaaS 연동 등 대부분의 일반적인 API

### GraphQL
<img width="1055" height="1491" alt="image" src="https://github.com/user-attachments/assets/c37532d8-8f85-47c9-896a-351d158577a8" />

- **배경과 시기**: 2012년 Facebook이 모바일 앱의 뉴스피드를 개발하면서 내부용으로 만들었고, 2015년에 오픈소스로 공개했습니다(2018년 GraphQL Foundation 설립). REST의 over/under-fetching 문제를 근본적으로 해결하려고 고안되었습니다.
- **장점**: 클라이언트가 필요한 필드만 정확히 요청합니다. 단일 엔드포인트에서 여러 자원을 한 번에 조회할 수 있고, 강력한 타입 스키마 덕분에 자동 문서화와 IDE 지원이 뛰어납니다.
- **단점**: HTTP 캐싱을 활용하기 어렵습니다. 복잡한 중첩 쿼리가 서버에 과부하를 줄 수 있어 쿼리 깊이 제한 같은 방어가 필요하고, N+1 쿼리 문제도 생깁니다. 초기 학습 곡선이 가팝니다.
- **응용분야**: 화면 구성이 복잡한 SNS·커머스 앱, 여러 마이크로서비스를 하나로 묶는 API 게이트웨이(BFF), GitHub·Shopify의 공개 API

### gRPC

<img width="1055" height="1491" alt="image" src="https://github.com/user-attachments/assets/c2d506e3-c50a-49ff-9872-87cc417b92a3" />

---

- **배경과 시기**: Google이 2001년경부터 내부에서 쓰던 RPC 프레임워크 "Stubby"를 개선해 2015년에 오픈소스로 공개했습니다(현재 CNCF 프로젝트). 수천 개의 마이크로서비스를 운영하면서 만들어진, 고성능 내부 통신 표준입니다.
- **장점**: 바이너리 직렬화와 HTTP/2 다중화 덕분에 JSON 기반 REST보다 훨씬 빠르고 가볍습니다. .proto 파일 하나로 여러 언어의 클라이언트/서버 코드를 자동 생성할 수 있어 개발 생산성이 높습니다.
- **단점**: 브라우저에서 직접 호출하기 어려워 gRPC-Web 같은 프록시가 필요합니다. 바이너리라 사람이 읽고 디버깅하기 어렵고, 스키마 관리와 학습 곡선도 가팝니다.
- **응용분야**: 마이크로서비스 간 내부 통신, 쿠버네티스 기반 클라우드 네이티브 시스템, 모바일-서버 간 고성능 통신, ML 모델 서빙(TensorFlow Serving 등)

## 2. 실시간·푸시형

### Webhook
<img width="1312" height="1199" alt="image" src="https://github.com/user-attachments/assets/186104d0-ee12-4c76-b663-7367c761b8c5" />

---

- **배경과 시기**: 2007년 개발자 Jeff Lindsay가 "웹을 위한 콜백"이라는 개념으로 이름을 붙였습니다. 외부 서비스에 "변경됐어?"라고 계속 물어보는 폴링(polling)의 낭비를 없애려고 시작됐습니다. 사실 구조 자체는 더 오래됐지만, Webhook이라는 명명과 개념화는 2007년 부터입니다.
- **장점**: 구현이 매우 단순합니다(그냥 HTTP POST를 받는 엔드포인트). 폴링이 필요 없어 자원을 아끼고 즉시 통지를 받을 수 있습니다.
- **단점**: 수신 서버가 공개 URL을 가져야 합니다. 전송 실패 시 재시도, 중복 수신, 순서 보장을 직접 처리해야 하고, 위조 요청을 막기 위한 서명 검증도 필요합니다.
- **응용분야**: 결제 완료 통지(Stripe, 토스페이먼츠), GitHub push 시 CI/CD 자동 빌드, 챗봇·메신저 연동, 자동화 도구(Zapier, n8n)

### WebSocket
- **배경과 시기**: HTML5 표준화 과정에서 등장해 2011년 RFC 6455로 표준화되었습니다. 그 전에는 실시간 웹을 구현하려고 Long Polling이나 Comet 같은 편법을 써야 했습니다.
- **장점**: 연결을 한 번 맺으면 서버와 클라이언트가 언제든 서로 메시지를 보낼 수 있습니다. 매 요청마다 붙던 HTTP 헤더 오버헤드가 없어 지연시간이 낮습니다.
- **단점**: 연결을 계속 유지하므로 서버 자원 부담이 크고, 수평 확장(로드밸런싱, 세션 관리)이 까다롭습니다. 연결이 끊겼을 때 재연결을 직접 처리해야 합니다.
- **응용분야**: 채팅·메신저, 온라인 게임, 주식·코인 실시간 시세, 협업 도구(실시간 공동 편집), 실시간 대시보드

### SSE (Server-Sent Events)
- **배경과 시기**: 2006년 Opera 브라우저가 처음 구현했고, 이후 HTML5 표준(EventSource API)에 포함되었습니다. 서버에서 클라이언트 방향으로만 데이터를 보내는 단순한 푸시입니다.
- **장점**: 일반 HTTP를 그대로 쓰므로 구현이 쉽고 기존 인프라(프록시, 인증)와 잘 호환됩니다. 브라우저가 자동 재연결과 이벤트 ID를 기본 지원합니다.
- **단점**: 서버에서 클라이언트로만 보내는 단방향 통신입니다. 텍스트 데이터만 지원하고, HTTP/1.1에서는 브라우저의 도메인당 동시 연결 수 제한(보통 6개)이 있습니다.
- **응용분야**: 알림 피드, 뉴스·스포츠 실시간 업데이트, 진행 상태 표시. 특히 최근에는 **ChatGPT·Claude 같은 LLM 서비스의 토큰 스트리밍 응답**에 표준으로 쓰입니다.

## 3. 메시징·이벤트형

### EDA (Event-Driven Architecture)
- **배경과 시기**: 프로토콜이라기보다 아키텍처 패턴입니다. 1990년대 메시지 지향 미들웨어(MOM)에서 출발했고, 2002년 David Luckham의 복합 이벤트 처리(CEP) 개념이 더해져 체계화되었습니다.
- **장점**: 생산자와 소비자가 서로를 몰라도 되는 느슨한 결합 구조입니다. 소비자를 쉽게 추가할 수 있고 확장성이 뛰어나며, 일부 서비스가 장애가 나도 다른 부분은 계속 작동합니다.
- **단점**: 데이터가 즉시가 아니라 결국 일치하는(eventual consistency) 구조라 설계가 어렵습니다. 흐름 추적과 디버깅이 힘들고, 이벤트 순서 보장, 중복 처리도 고민해야 합니다.
- **응용분야**: 이커머스 주문 처리(주문→결제→재고→배송), 실시간 데이터 파이프라인, 로그·클릭스트림 분석, 금융 이상거래 탐지

### AMQP (Advanced Message Queuing Protocol)
- **배경과 시기**: 2003년 JPMorgan Chase의 John O'Hara가 시작했습니다. 당시 금융권 메시징은 IBM MQ, TIBCO 같은 고가의 독점 제품에 묶여 있어 서로 호환되지 않았습니다. 오픈 표준이 필요했고, 2011년 AMQP 1.0이 ISO/IEC 표준이 됐습니다.
- **장점**: Exchange를 통한 유연한 라우팅(direct, topic, fanout), 메시지 영속성, 전달 확인(ACK), 트랜잭션 등 신뢰성 있는 메시징 기능이 풍부합니다. 벤더 간 호환성을 보장합니다.
- **단점**: MQTT보다 무겁고 프로토콜이 복잡합니다. 0-9-1과 1.0 버전 간 차이가 커서 혼란스럽고, Kafka 같은 대용량 스트리밍과 비교하면 처리량에 한계가 있습니다.
- **응용분야**: 금융 거래 메시징, 비동기 작업 큐(이메일 발송, 이미지 처리 같은 백그라운드 작업), 마이크로서비스 간 비동기 통신(RabbitMQ, Azure Service Bus)

### MQTT (Message Queuing Telemetry Transport)
- **배경과 시기**: 1999년 IBM의 Andy Stanford-Clark와 Arcom의 Arlen Nipper가 설계했습니다. 사막의 석유 파이프라인 센서 데이터를 비싸고 불안정한 위성 통신으로 보내야 했던 상황에서 만들어졌습니다. 2013년 OASIS 표준, 2014년 ISO/IEC 표준이 됐습니다.
- **장점**: 헤더가 최소 2바이트일 정도로 극도로 가볍습니다. 브로커를 통한 발행/구독 구조이고, QoS 0/1/2 단계로 전달 보장 수준을 고를 수 있습니다. 불안정한 네트워크 환경에 최적화됐습니다.
- **단점**: 브로커가 단일 장애점이 될 수 있습니다. 기본 보안 기능이 약해 TLS와 인증을 별도로 구성해야 하고, 대용량 데이터나 복잡한 라우팅에는 맞지 않습니다.
- **응용분야**: IoT 센서 데이터 수집, 스마트홈(Home Assistant 등), 커넥티드카, 스마트팩토리, 원격 검침. Facebook Messenger도 초기에 모바일 배터리 절약을 위해 MQTT을 썼습니다.

## 4. 기업 간 데이터 교환

### EDI (Electronic Data Interchange)
- **배경과 시기**: 그림의 기술 중 가장 오래되었습니다. 1948년 베를린 공수작전 때 물자 목록을 표준화한 것이 기원으로 꼽히고, 1960~70년대 운송업계에 본격 도입됐습니다. 종이 서류를 완전히 없애기 위한 "최초의 디지털 표준화"입니다. 지금도 대형 유통사·제조사에서 공급사와의 발주 문서는 EDI로만 처리됩니다.
- **장점**: 거래 문서 처리를 완전 자동화해 인건비와 입력 오류를 크게 줄이고 처리 속도를 높입니다. 업계 표준이 확립되어 있어 대규모 공급망에서 상호 호환성을 보장합니다.
- **단점**: 초기 구축 비용과 VAN(부가가치통신망) 이용료가 높습니다. 포맷이 경직되고 난해해서 전문 인력이 필요하고, 중소기업에게는 진입장벽이 높습니다.
- **응용분야**: 유통·제조 공급망(대형마트와 납품업체 간 발주·송장), 무역·통관, 물류, 의료보험 청구

## 등장 시기 한눈에 보기

| 시기 | 기술 | 핵심 동기 |
|---|---|---|
| 1960~70년대 | EDI | 종이 문서 수작업 제거 |
| 1990년대~ | EDA (개념) | 시스템 간 느슨한 결합 |
| 1998~2003 | SOAP | 방화벽을 통과하는 분산 호출 |
| 1999 | MQTT | 위성망 같은 저대역 환경의 센서 통신 |
| 2000 | REST | 웹의 확장 원리를 API에 적용 |
| 2003 | AMQP | 독점 메시징 제품 탈피 |
| 2006 | SSE | 가벼운 서버 푸시 |
| 2007 | Webhook | 폴링 낭비 제거 |
