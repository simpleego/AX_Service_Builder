# 프로젝트 역할 분담
AI를 활용해 프로젝트를 진행하는 4인 팀이라면, 프론트엔드 1명, 백엔드 1명, AI 1명, PM 1명처럼 기술 영역만 나누는 것보다, 각자 명확한 책임 영역을 갖고 실제 기능을 끝까지 완성하도록 역할을 나누는 것이 중요합니다.

AI를 활용하면 코드 작성 속도는 빨라지지만, 오히려 다음과 같은 문제가 생기기 쉽습니다.

- 네 명이 같은 기능을 중복해서 개발한다.
- AI가 생성한 코드의 구조와 품질을 제대로 이해하는 사람이 없다.
- 프론트엔드와 백엔드의 API 규격이 맞지 않아 통합이 늦어진다.
- 일부 팀원에게 작업이 몰리고, 나머지는 무엇을 해야 할지 모른다.
- 각자 개발은 했지만 최종적으로 서비스가 연결되지 않는다.

이 문제를 해결하려면 역할은 명확하게 나누되, 모든 팀원이 풀스택 관점에서 프로젝트 전체를 이해하는 구조로 운영하는 것이 좋습니다.

## 1. 4인 팀에 맞는 역할 분담

## 팀원 A — 프론트엔드 및 사용자 경험

UI/UX · 화면 개발 · API 연동

- 화면 구조와 사용자 흐름 설계
- 공통 컴포넌트 및 페이지 개발
- 백엔드 API 연결, 로딩·오류 상태 처리
- 사용자 관점의 기능 테스트
  주요 산출물: 동작하는 화면, 컴포넌트, API 연동 코드

## 팀원 B — 백엔드 및 데이터

API · DB · 인증 · 보안

- 데이터베이스 설계 및 모델 정의
- API 명세와 서버 로직 구현
- 로그인·권한·입력 검증·예외 처리
- 데이터 저장과 조회의 안정성 확보
  주요 산출물: API 명세, DB 스키마, 서버 코드, 테스트

## 팀원 C — AI 기능 및 서비스 로직

LLM · RAG · 프롬프트 · 평가

- AI가 해결할 문제와 입출력 정의
- 모델/API 연동 및 프롬프트 관리
- 필요하면 RAG, 임베딩, 검색 파이프라인 구현
- 응답 품질·지연 시간·비용 검증
  주요 산출물: AI 모듈, 입출력 규격, 평가 결과

## 팀원 D — 기술 통합 및 배포 책임

아키텍처 · CI/CD · 통합 테스트 · 일정

- 전체 시스템 구조와 인터페이스 조율
- Git 브랜치·PR·코드 리뷰 규칙 관리
- 개발 환경, 배포, 로그 및 모니터링 구성
- 통합 테스트와 작업 진행 상황 관리
  주요 산출물: 실행 가능한 통합 서비스, 배포 환경, 테스트 결과

단, 이 구성은 시작점일 뿐입니다. 팀원 D가 단순한 회의 관리자나 잡무 담당자가 되어서는 안 됩니다. 실제 기술 작업을 맡으면서 통합을 책임져야 합니다. AI 기능이 프로젝트의 핵심이 아니라면 C의 역할을 일반 백엔드·도메인 로직 개발로 바꾸고 AI 기능은 팀원들이 함께 맡는 편이 낫습니다.

## 2. 더 중요한 원칙: 기술별 담당과 기능별 책임을 함께 둔다

위와 같이 기술 영역을 나누기만 하면 문제가 남습니다. 예를 들어 A는 화면을 만들고, B는 API를 만들었는데 서로 연결이 안 되면 누가 해결할까요?

그래서 기술별 담당 외에 기능별 오너(Feature Owner) 를 지정해야 합니다.

예를 들어 AI 기반 문서 분석 서비스를 만든다면 다음처럼 나눌 수 있습니다.

| 기능 | 주 담당자 | 협업 담당자 | 완료 기준 |
| --- | --- | --- | --- |
| 회원가입·로그인 | B | A | 가입부터 로그인까지 동작 |
| 문서 업로드 | A | B | 파일 업로드 및 저장 성공 |
| AI 문서 분석 | C | B | 입력 문서에 대한 분석 결과 반환 |
| 분석 결과 화면 | A | C | 결과가 화면에 정상 표시 |
| 전체 서비스 배포 | D | 전원 | 다른 환경에서도 실행 가능 |

여기서 중요한 점은 주 담당자가 해당 기능의 완료까지 책임진다는 것입니다. 담당자가 모든 코드를 혼자 작성해야 한다는 뜻은 아닙니다. 다른 팀원이 코드를 작성하거나 리뷰할 수 있지만, 기능의 완성 여부를 확인할 사람은 한 명이어야 합니다.

예를 들어 AI 분석 기능은 C가 오너여도 다음 작업은 협업으로 진행할 수 있습니다.

- C: AI 처리 로직과 응답 형식 구현
- B: 문서 및 분석 결과 저장 API 구현
- A: 분석 요청과 결과 표시 화면 구현
- D: 실제 서버와 AI 모듈의 통합 테스트 및 배포

이렇게 하면 각자 전문 분야가 있으면서도 결과적으로 하나의 기능을 완성하게 됩니다.

## 3. AI를 활용하는 팀이라면 개발 순서를 바꿔야 한다

AI 코딩 도구를 사용할 때는 각자 독립적으로 코드를 생성하기 전에 인터페이스부터 합의하는 것이 중요합니다.

1단계. 요구사항과 완료 기준 합의

사용자가 무엇을 할 수 있어야 하는지, 성공과 실패를 어떻게 판단할지 정합니다.

2단계. API·데이터 규격 먼저 확정

요청 필드, 응답 JSON, 오류 형식, DB 구조를 정합니다. 프론트엔드와 백엔드는 이 규격을 기준으로 병렬 개발합니다.

3단계. 각자 AI를 활용해 구현

각 담당자는 자신의 작업 범위, 기존 코드 구조, 수정 금지 영역, 테스트 조건을 AI에 알려줍니다. 다른 담당자의 파일을 임의로 변경하지 않도록 합니다.

4단계. PR 리뷰 후 통합

코드가 생성됐다는 이유만으로 완료 처리하지 않습니다. 테스트 통과, 기존 기능 유지, 보안 및 인터페이스 확인 후 병합합니다.

5단계. 실제 사용자 시나리오로 검증

화면에서 입력하고, 서버가 처리하고, DB에 저장되고, 결과가 다시 표시되는 전체 흐름을 확인합니다.

예를 들어 다음과 같은 API 계약을 먼저 작성할 수 있습니다.

json
```
POST /api/documents/analyze

{
  "documentId": "doc_123"
}
```

응답 규격도 함께 정합니다.

json
```
{
  "status": "completed",
  "summary": "문서의 핵심 요약",
  "keywords": ["AI", "프로젝트"]
}
```

이것은 단순한 예시이지만, 프론트엔드 담당자는 이 규격에 맞춰 화면을 개발하고 백엔드·AI 담당자는 같은 규격에 맞춰 서버를 구현할 수 있습니다. 실제 AI 처리 중 대기 시간이 발생한다면 `processing` 상태나 비동기 작업 방식도 미리 합의하면 됩니다.

## 4. 팀 운영 규칙은 최소한으로, 하지만 반드시 정한다

역할 분담이 잘 안 되는 팀은 역할표가 없어서라기보다, 누가 무엇을 언제까지 어떤 기준으로 끝내야 하는지가 불분명한 경우가 많습니다.

다음 5가지 규칙을 추천합니다.

| 규칙 | 운영 방법 |
| --- | --- |
| 작업은 한 명이 책임진다 | 모든 작업에 담당자 1명 지정 |
| 작업 크기를 작게 나눈다 | 1\~2일 안에 완료할 수 있는 단위로 분리 |
| 인터페이스를 먼저 합의한다 | API, 데이터 구조, 함수 입출력부터 정의 |
| 작업은 공유 저장소에 통합한다 | PR과 코드 리뷰를 거쳐 병합 |
| 매일 막힌 부분을 공유한다 | 진행 상황, 다음 작업, 장애 요소만 짧게 공유 |

특히 AI가 만든 코드는 담당자가 직접 읽고 설명할 수 있어야 합니다. AI가 작성한 코드라고 해서 자동으로 유지보수할 수 있는 코드가 되는 것은 아닙니다.

### 매일 15분 회의 예시

각 팀원이 다음 세 가지만 이야기하도록 합니다.

1. 어제 무엇을 완료했는가?
2. 오늘 무엇을 완료할 것인가?
3. 다른 팀원의 도움이 필요한 부분은 무엇인가?

회의에서 긴 기술 토론을 진행하기보다, 문제가 발견되면 관련 담당자끼리 별도로 해결하는 것이 효율적입니다.

## 5. 2주 프로젝트라면 이렇게 진행한다

### 1\~2일

설계 및 환경 구축

요구사항, 화면 흐름, DB, API 계약을 합의하고 모두가 실행할 수 있는 개발 환경을 구축합니다.

### 3\~6일

핵심 기능 병렬 개발

각자 담당 영역을 개발하되, 첫날부터 가짜 데이터나 Mock API로 화면과 서버를 연결합니다.

### 7\~10일

통합 및 오류 수정

실제 DB와 AI를 연결하고, 담당 영역 사이의 오류를 해결합니다. 새 기능 추가보다 핵심 흐름의 완성을 우선합니다.

### 11\~14일

테스트 및 배포

실제 사용 시나리오를 검증하고, 오류·성능·보안 문제를 수정한 뒤 최종 배포합니다.

이 일정에서 가장 중요한 것은 프로젝트 마지막 날에 처음으로 전체 시스템을 연결하지 않는 것입니다. 적어도 초기 개발 단계부터 전체 흐름이 동작하는 작은 버전을 만들어야 합니다.

## 6. 최종적으로 권장하는 운영 원칙

4인 팀에서는 다음과 같이 기억하면 좋습니다.

- 각자 전문 분야는 분명하게: 프론트엔드, 백엔드, AI, 통합·배포.
- 기능의 최종 책임자는 한 명: 여러 명이 참여해도 완료 여부를 확인할 담당자는 명확하게.
- 모두가 전체 흐름을 이해: 자기 코드만 작성하고 끝내지 않기.
- AI는 개발 보조자: 설계 결정, 코드 검증, 테스트, 최종 책임은 팀원이 맡기.
- 개발과 통합을 동시에 진행: 모든 기능을 만든 뒤 한꺼번에 연결하지 않기.

## 팀 상황에 맞게 역할을 구체화해 보겠습니다

사실 가장 좋은 분담 방식은 팀원들의 실력과 프로젝트 성격에 따라 달라집니다. 아래 세 가지를 알려주시면 실제로 사용할 수 있는 4인 팀 역할 분담표와 작업 배정 방식을 구체적으로 설계해 드릴 수 있습니다.

1. 어떤 프로젝트를 개발하고 있나요?

ai AI 서비스를 포함한 웹 프로젝트

일반적인 웹 서비스 (CRUD, 게시판, 쇼핑몰 등)

AI 에이전트 또는 RAG 기반 서비스

기타 프로젝트

모두 초보자 또는 입문자
