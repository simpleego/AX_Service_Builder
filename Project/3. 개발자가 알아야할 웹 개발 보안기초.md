# 웹사이트 개발 필수 보안: 시대별 정리

웹 보안은 **"웹이 새로운 기능을 얻을 때마다 새로운 공격면이 생기는"** 흐름으로 발전해 왔습니다.

---

## 1. 1990년대: 정적 웹과 CGI(Common Gateway Interface) 시대

**배경**: 웹이 문서를 보여주는 수준에서 CGI(Perl, C)로 서버 프로그램을 실행하기 시작했습니다. 보안 개념이 거의 없었고 통신은 평문 HTTP(HyperText Transfer Protocol)였습니다.

**주요 위협**
- **도청**: 비밀번호와 카드번호가 평문으로 전송되었습니다. 이를 막기 위해 Netscape가 1995년 SSL(Secure Sockets Layer)을 내놓았고, 이것이 오늘날 HTTPS(HyperText Transfer Protocol Secure)와 TLS(Transport Layer Security)의 시작입니다.
- **명령어 주입(Command Injection)**: 사용자 입력이 그대로 쉘 명령에 들어가 서버 명령이 실행되었습니다.
- **디렉터리 트래버설(Directory Traversal)**: `../`로 상위 경로에 접근해 설정 파일 같은 서버 파일을 읽어냈습니다.
- **기본 설정 방치**: 기본 계정·비밀번호, 디렉터리 목록 노출, 상세 에러 메시지 노출

**지금도 유효한 교훈**: 사용자 입력은 절대 신뢰하지 않는다, 최소 권한으로 실행한다, 불필요한 기능은 끈다.

## 2. 2000년대 초중반: 동적 웹과 데이터베이스 시대

**배경**: PHP(PHP: Hypertext Preprocessor), ASP(Active Server Pages), JSP(JavaServer Pages)와 DB(Database)가 결합하면서 게시판, 회원가입, 쇼핑몰이 폭발적으로 늘었습니다. 2001년 OWASP(Open Worldwide Application Security Project, 2023년 이전 명칭은 Open Web Application Security Project)가 설립되었고, 2003년 첫 **OWASP Top 10**이 발표되었습니다.

**주요 위협**
- **SQL(Structured Query Language) Injection**: 입력값이 SQL 문에 그대로 붙어 DB 전체가 털리는 공격입니다. 1998년 처음 문서화되었고, 10년 넘게 가장 큰 유출 원인이었습니다.
- **XSS(Cross-Site Scripting)**: 게시글 등에 악성 스크립트를 심어 다른 사용자의 브라우저에서 실행시킵니다. 2005년 MySpace의 Samy 웜은 하루 만에 100만 명 이상에게 퍼졌습니다.
- **CSRF(Cross-Site Request Forgery)**: 로그인된 사용자가 모르는 사이 송금, 비밀번호 변경 같은 요청을 보내게 만듭니다.
- **세션 하이재킹 / 세션 고정**: 쿠키(세션 ID(Identifier))를 탈취하거나 미리 정해둔 세션 ID를 쓰게 만듭니다.
- **파일 업로드 취약점**: 이미지 대신 웹셸(서버 실행 스크립트)을 업로드합니다. 국내 웹 해킹에서 특히 많았던 유형입니다.

**필수 대응**
- SQL은 **Prepared Statement(파라미터 바인딩)** 또는 ORM(Object-Relational Mapping) 사용
- 출력 시 HTML(HyperText Markup Language) **인코딩/이스케이프**, 템플릿 엔진의 자동 이스케이프 활용
- 상태 변경 요청에 **CSRF 토큰** 적용
- 세션 쿠키에 **HttpOnly, Secure** 속성 부여, 로그인 시 세션 ID 재발급
- 업로드 파일의 확장자와 MIME(Multipurpose Internet Mail Extensions) 타입 검사, 웹 루트 밖 저장, 실행 권한 제거

## 3. 2000년대 후반~2010년대 초: Web 2.0과 대규모 유출 시대

**배경**: AJAX(Asynchronous JavaScript and XML)와 SNS(Social Networking Service)로 웹이 애플리케이션처럼 바뀌었고, 사용자 수가 수천만 단위가 되면서 한 번의 유출 피해가 막대해졌습니다. 국내에서도 2011년 SK컴즈(네이트·싸이월드) 3,500만 명 유출 등 대형 사고가 이어졌습니다.

**주요 위협**
- **비밀번호 저장 방식 문제**: 평문 저장이나 솔트 없는 MD5(Message-Digest algorithm 5) 또는 SHA-1(Secure Hash Algorithm 1) 해시는 유출 시 대부분 즉시 복원됩니다(2012년 LinkedIn 유출 사례).
- **클릭재킹(Clickjacking, 2008)**: 투명한 iframe(inline frame)을 덮어 사용자가 의도하지 않은 버튼을 누르게 만듭니다.
- **공개 Wi-Fi 세션 탈취**: 2010년 Firesheep 도구가 HTTP 쿠키 탈취를 클릭 한 번으로 보여주면서, 로그인 페이지만이 아니라 **전체 사이트 HTTPS**가 필요하다는 인식이 퍼졌습니다.
- **인프라 취약점**: 2014년 Heartbleed(OpenSSL), Shellshock(Bash, Bourne-Again SHell)처럼 웹 앱 코드가 아니라 서버 소프트웨어 자체의 취약점이 대량 피해를 냈습니다.

**필수 대응**
- 비밀번호는 **bcrypt, scrypt, Argon2** 같은 느린 해시와 솔트로 저장
- **보안 헤더**: `X-Frame-Options` 또는 CSP(Content Security Policy)의 `frame-ancestors`(클릭재킹 방지), HSTS(HTTP Strict Transport Security, HTTPS 강제)
- **전 구간 HTTPS**: 2015년 Let's Encrypt 등장으로 무료 인증서가 보편화되었고, 2018년 Chrome이 HTTP 사이트에 "주의 요함" 표시를 시작했습니다.
- **CSP**: 허용된 출처의 스크립트만 실행하게 해 XSS 피해를 줄임
- 서버·라이브러리의 **정기 패치**

## 4. 2010년대 중후반: API, SPA, 클라우드 시대

**배경**: React, Vue 같은 SPA(Single Page Application)와 모바일 앱이 늘면서 서버는 화면이 아니라 REST(Representational State Transfer) API(Application Programming Interface)를 제공하게 되었습니다. 서버도 AWS(Amazon Web Services) 같은 클라우드로 옮겨갔습니다. 공격 대상이 웹 페이지에서 **API와 클라우드 설정**으로 이동했습니다.

**주요 위협**
- **접근 제어 실패**: 대표 유형인 IDOR(Insecure Direct Object Reference)는 `/api/orders/1001`을 `1002`로 바꾸기만 해도 남의 주문이 보이는 문제입니다. 2021년 OWASP Top 10에서 **1위**로 올라섰습니다.
- **토큰 관련 실수**: JWT(JSON Web Token) 서명 미검증, 알고리즘을 `none`으로 바꾸는 공격, 토큰을 localStorage에 저장해 XSS로 탈취되는 경우가 있습니다. 여기서 JSON은 JavaScript Object Notation입니다.
- **CORS(Cross-Origin Resource Sharing) 오설정**: `Access-Control-Allow-Origin: *`과 인증 정보 허용을 함께 써서 다른 사이트가 API를 호출할 수 있게 됩니다.
- **SSRF(Server-Side Request Forgery)**: 서버가 공격자가 지정한 내부 주소로 요청을 보내게 만듭니다. 2019년 Capital One 1억 명 유출이 클라우드 메타데이터 서버를 노린 SSRF였습니다.
- **클라우드 설정 오류**: 공개로 열린 S3(Simple Storage Service) 버킷, GitHub에 커밋된 API 키나 DB 비밀번호
- **미패치 프레임워크**: 2017년 Equifax 1억 4천만 명 유출은 이미 패치가 나온 Apache Struts 취약점을 방치한 결과였습니다.
- **크리덴셜 스터핑(Credential Stuffing)**: 다른 사이트에서 유출된 아이디/비밀번호 조합을 자동으로 대입합니다.

**필수 대응**
- **모든 API 요청마다 서버에서 권한 검사**(프론트엔드 숨김 처리는 보안이 아님)
- 검증된 표준 사용: OAuth(Open Authorization) 2.0과 OIDC(OpenID Connect). JWT는 서명·만료·발급자 검증 필수
- CORS는 허용 출처를 명시적으로 지정
- 서버가 외부 URL(Uniform Resource Locator)을 요청할 때 허용 목록 적용, 내부 IP(Internet Protocol) 대역 차단
- **비밀정보는 환경변수나 Secret Manager로 관리**하고 Git에 절대 커밋하지 않기(`.gitignore`, git-secrets)
- **Rate Limiting**, 로그인 실패 제한, MFA(Multi-Factor Authentication)

## 5. 2020년대: 공급망과 제로트러스트 시대

**배경**: 현대 웹 프로젝트는 코드의 대부분이 npm(Node Package Manager), PyPI(Python Package Index) 같은 저장소의 오픈소스 의존성입니다. 내가 쓴 코드가 안전해도 **내가 가져다 쓴 코드**가 뚫리는 시대가 되었습니다.

**주요 위협**
- **Log4Shell(2021)**: 거의 모든 Java 서비스가 쓰던 로깅 라이브러리 Log4j의 원격 코드 실행 취약점으로, 전 세계가 긴급 대응에 나섰습니다.
- **공급망 공격**: SolarWinds(2020) 빌드 시스템 침투, 2024년 xz-utils 백도어(수년간 신뢰를 쌓은 기여자가 심음), 2024년 polyfill.io CDN(Content Delivery Network) 도메인이 매각된 뒤 수십만 사이트에 악성 코드가 배포된 사건
- **악성 패키지와 타이포스쿼팅(Typosquatting)**: `requests` 대신 `reqeusts` 같은 이름으로 악성 패키지를 올리는 수법
- **경계 기반 보안의 한계**: 원격근무와 클라우드로 "내부망은 안전하다"는 전제가 무너졌습니다.

**필수 대응**
- **의존성 관리**: lock 파일 사용, `npm audit`, Dependabot, Snyk 등으로 취약점 자동 점검
- 외부 CDN 스크립트에는 SRI(Subresource Integrity) 해시 적용, 가능하면 직접 호스팅
- SBOM(Software Bill of Materials)으로 사용 중인 구성요소 파악
- **제로트러스트(Zero Trust)**: 내부 요청도 매번 인증·인가
- **쿠키 SameSite 속성**(2020년 Chrome이 기본값을 Lax로 변경해 CSRF 위험 감소)
- **패스키(Passkey)**: 2022년부터 Apple, Google, Microsoft가 본격 도입한 비밀번호 없는 인증

## 6. 2023년~현재: AI 시대

**배경**: 웹 서비스에 LLM(Large Language Model)이 들어가고, 개발자도 AI(Artificial Intelligence)로 코드를 생성하면서 완전히 새로운 공격면이 생겼습니다. OWASP도 2023년 **LLM 애플리케이션용 Top 10**을 별도로 발표했습니다.

**주요 위협**
- **프롬프트 인젝션(Prompt Injection)**: 사용자 입력이나 AI가 읽는 웹페이지·문서에 숨긴 지시문으로 시스템 프롬프트를 무력화하거나 데이터를 유출시킵니다. SQL Injection의 AI 버전으로 볼 수 있지만, 완벽한 차단 방법이 아직 없다는 점이 다릅니다.
- **API 키 노출**: OpenAI·Anthropic API 키를 프론트엔드 코드에 넣어 배포하는 실수가 매우 흔합니다.
- **과도한 권한을 가진 AI 에이전트**: AI에게 DB 쓰기, 메일 발송, 결제 같은 도구 권한을 주면 인젝션 한 번으로 실제 행동이 일어납니다.
- **AI 생성 코드의 취약점**: 검증 없이 붙여 넣은 코드에 SQL Injection이나 하드코딩된 비밀정보가 포함되는 경우
- **존재하지 않는 패키지 추천**: AI가 지어낸 패키지명을 공격자가 선점해 악성 패키지로 등록하는 수법(Slopsquatting)

**필수 대응**
- LLM API 키는 **반드시 백엔드에서만** 사용
- LLM 출력도 사용자 입력처럼 **신뢰하지 않는 데이터**로 취급(HTML에 넣을 때 이스케이프, SQL·쉘에 직접 넣지 않기)
- AI 에이전트에는 **최소 권한**만 부여하고, 중요한 행동은 사람 승인 단계 두기
- AI가 생성한 코드와 추천 패키지는 반드시 검토 후 사용

## 정리: 시대가 바뀌어도 변하지 않는 원칙

| 원칙 | 1990년대 | 2000년대 | 2010년대 | 2020년대~ |
|---|---|---|---|---|
| 입력을 신뢰하지 말라 | 명령어 주입 | SQL Injection, XSS | API 파라미터 조작 | 프롬프트 인젝션 |
| 전송을 보호하라 | SSL 등장 | 로그인만 HTTPS | 전체 HTTPS, HSTS | TLS 1.3 기본 |
| 인증·인가를 제대로 | 기본 계정 | 세션 관리 | OAuth, JWT, MFA | 패스키, 제로트러스트 |
| 최소 권한 | 서버 실행 권한 | DB 계정 권한 | 클라우드 IAM(Identity and Access Management) | AI 에이전트 권한 |
| 최신 상태 유지 | 서버 패치 | 프레임워크 패치 | 라이브러리 패치 | 공급망 전체 관리 |

결국 대부분의 사고는 **"신뢰할 수 없는 데이터를 코드나 명령으로 실행하게 두는 것"**과 **"권한 확인을 빠뜨리는 것"**이라는 두 가지 뿌리에서 나옵니다.   
실무 기준표로는 OWASP Top 10, OWASP API Security Top 10, OWASP Top 10 for LLM Applications를 함께 참고하시면 좋습니다.
