# React v18 소스 기반 강의안: Chapter 08–15

이 강의는 원본 코드를 읽고 동작을 예측한 뒤, 요구사항을 추가해 스스로 구현하는 순서로 진행한다. 코드 블록에서 ‘핵심 발췌’는 전체 실행 파일이 아니다. 실행 가능한 완성 코드는 `examples/src`에 있으며, 원본은 `reference/src`에 보관했다.

분석 대상: [원본 고정 커밋](https://github.com/soaple/first-met-react-practice-v18/tree/3adbe9bf8a01109abb0b675ace9ae1e0eaf8af41/src). 다음 설명의 ‘원본’은 모두 이 커밋을 뜻한다. 목표는 React 18의 함수 컴포넌트 작성법을 이해하는 것이며 최신 React 전용 기능을 다루지는 않는다.

## 0. 시작 전 공통 개념

컴포넌트 함수는 props와 현재 상태를 바탕으로 JSX를 계산한다. DOM을 직접 찾아 글자를 바꾸기보다, 상태를 바꾸고 다음 렌더에서 화면을 계산한다. props는 부모가 주는 입력이고 state는 해당 컴포넌트가 소유한 기억이다.

```text
사용자 조작 → 이벤트 핸들러 → 상태 갱신 요청
                          ↓
                다음 렌더의 JSX 계산 → 화면 반영
```

수업에서 매번 묻는 세 가지 질문은 “무슨 값이 바뀌는가?”, “누가 그 값을 소유하는가?”, “어떤 JSX가 그 값에 의존하는가?”다. 이 질문으로 이벤트, 리스트, 폼, Context를 같은 흐름에서 설명할 수 있다.

원본의 `src/index.js`는 여러 챕터를 import하지만 `<Blocks />`만 렌더링한다. import했다고 모두 화면에 나오는 것은 아니다. 추가 예제 앱에서는 상단 버튼으로 8~15장을 선택한다.

## 08. 이벤트 처리 — ConfirmButton

### 학습 목표

- 함수를 이벤트 prop에 전달하고, 렌더 시 호출과 구분한다.
- 상태 값에 따라 텍스트와 disabled 속성을 함께 바꾼다.
- 토글과 일회성 확인의 요구사항 차이를 설명한다.

### 원본 읽기

대상: [ConfirmButton.jsx](https://github.com/soaple/first-met-react-practice-v18/blob/3adbe9bf8a01109abb0b675ace9ae1e0eaf8af41/src/chapter_08/ConfirmButton.jsx).

`useState(false)`의 첫 값은 아직 확인하지 않았다는 뜻이다. `handleConfirm`은 이전 상태를 받아 부정한 값을 반환한다. JSX의 `onClick`에는 이 함수 자체를 전달한다. `disabled={isConfirmed}`와 버튼 내부의 삼항 연산자가 같은 상태를 사용하므로 동작과 문구가 함께 바뀐다.

| 시점 | isConfirmed | 문구 | disabled |
|---|---|---|---|
| 최초 렌더 | false | 확인하기 | false |
| 첫 클릭 이후 | true | 확인됨 | true |
| 두 번째 클릭 시도 | true | 확인됨 | true |

중요한 관찰: 핸들러는 토글이지만 버튼은 첫 클릭 뒤 비활성화된다. 따라서 일반적인 사용자 조작으로 두 번째 토글이 일어나지 않는다. ‘확인 완료’라는 목적에는 `setIsConfirmed(true)`가 더 직접적인 표현이다.

### 이론과 기술

React 이벤트 이름은 `onClick`처럼 작성한다. `onClick={handleConfirm}`은 나중에 호출할 함수를 전달한다. `onClick={handleConfirm()}`은 렌더 중 함수를 실행하고 반환값을 전달하므로 의도와 다르다. 인자가 필요하면 `onClick={() => handleSelect(id)}`처럼 감싼다. 이벤트 객체가 필요한 핸들러는 매개변수로 받아 사용한다. [공식 이벤트 설명](https://react.dev/learn/responding-to-events).

이전 상태로 다음 값을 계산할 때는 `setValue(previous => !previous)` 패턴을 사용한다. 반면 “완료 상태로 만든다”는 요청에는 이전 값이 필요하지 않으므로 `setValue(true)`가 적합하다. setter 직후 현재 함수 안의 변수가 즉시 다른 값으로 바뀐다고 가정하지 않는다.

폼 안에서 사용하는 일반 버튼에는 `type="button"`을 지정해 제출 동작과 구분한다. 화면에 보이는 문구만 바꾸지 말고 실제 disabled 속성도 상태에 연결한다.

### 추가 예제와 설명

완성 파일: `examples/src/chapter_08.jsx`. 확인과 초기화 행동을 분리했다. 핵심 발췌:

```jsx
const [confirmed, setConfirmed] = useState(false);
<button type="button" disabled={confirmed}
  onClick={() => setConfirmed(true)}>확인하기</button>
<button type="button" disabled={!confirmed}
  onClick={() => setConfirmed(false)}>다시 확인</button>
```

두 버튼은 반대 상태에서 활성화된다. `role="status"` 문단은 상태 변화를 텍스트로 전달한다. 원본의 컴포넌트와 달리 재시도 가능한 학습 UI다.

### 실습

1. 원본을 실행하기 전에 첫 클릭과 두 번째 클릭 결과를 말한다.
2. 추가 예제에서 확인 → 다시 확인 → 확인을 반복한다.
3. 확장 과제: 확인 취소 시 브라우저 confirm으로 의사를 확인하고, 취소를 선택하면 상태를 유지한다.

완료 기준: 첫 클릭 후 확인 버튼은 비활성화되고, 초기화 후 다시 활성화된다. 상태를 직접 대입하거나 DOM의 disabled를 직접 바꾸지 않는다.

### 확인 문제와 해설

- Q: `onClick={setConfirmed(true)}`는 왜 문제인가? A: 렌더 중 setter를 실행하기 때문이다. 함수를 전달하도록 감싸야 한다.
- Q: 토글 updater를 쓰면 비활성화된 버튼도 되돌릴 수 있는가? A: 아니다. 비활성화 상태에서는 그 버튼으로 다음 클릭을 실행할 수 없다.
- Q: 실제 서버 등록의 중복 요청도 이 예제만으로 해결되는가? A: 아니다. 이 예제는 로컬 UI 상태다. 서버 처리 상태와 중복 요청 정책은 별도 설계가 필요하다.

## 09. 조건부 렌더링 — LandingPage와 Toolbar

### 학습 목표

- if, `&&`, 삼항 연산자의 선택 기준을 설명한다.
- 상태를 부모에 두고 자식에는 값과 콜백을 전달한다.
- 화면 분기와 실제 인증을 구분한다.

### 원본 읽기

대상: [LandingPage.jsx와 Toolbar.jsx](https://github.com/soaple/first-met-react-practice-v18/tree/3adbe9bf8a01109abb0b675ace9ae1e0eaf8af41/src/chapter_09).

LandingPage가 `isLoggedIn`을 소유한다. 로그인 콜백은 true, 로그아웃 콜백은 false를 저장한다. Toolbar에는 상태 한 개와 콜백 두 개를 전달한다. Toolbar는 구조 분해로 props를 꺼내 환영 문구와 버튼을 선택한다.

| 파일 | 책임 | 상태 소유 |
|---|---|---|
| LandingPage | 로그인 여부 변경, 전체 화면 구성 | isLoggedIn |
| Toolbar | 받은 상태로 문구와 버튼 표시 | 없음 |

`isLoggedIn && <span>`은 참일 때만 인사말을 포함한다. 삼항 연산자는 로그인 버튼과 로그아웃 버튼 중 하나를 선택한다. 아래의 “리액트 공부” 문구는 조건 바깥이므로 항상 보인다.

### 이론과 기술

조건이 거짓일 때 아무것도 표시하지 않으려면 `&&`, 두 화면 중 하나를 고르면 삼항 연산자, 분기가 길면 JSX 전에 if로 반환하는 방식을 고려한다. `0 && <p>`는 0을 렌더링할 수 있으므로 배열 길이 조건은 `items.length > 0 && ...`처럼 불리언으로 만든다. [공식 조건부 렌더링 설명](https://react.dev/learn/conditional-rendering).

자식은 props를 직접 바꾸지 않는다. “로그인 요청”이라는 의도를 부모 콜백으로 전달하고, 부모의 상태 변경 결과를 다시 받는다. Toolbar에 같은 로그인 상태를 또 만들면 부모와 자식의 값이 어긋날 수 있다.

### 추가 예제와 설명

완성 파일: `examples/src/chapter_09.jsx`. 불리언 대신 `user: null | { id, name }`을 사용한다. 로그인 여부와 사용자 이름을 하나의 데이터에서 얻으므로 `isLoggedIn`과 `user`를 따로 맞출 필요가 없다.

```jsx
const [user, setUser] = useState(null);
<Toolbar user={user}
  onLogin={() => setUser({ id: 1, name: '학습자' })}
  onLogout={() => setUser(null)} />
```

이 객체는 고정된 체험 데이터다. API 호출, 토큰, 세션은 없으며 UI 전환을 학습한다. 조건부로 회원 화면을 숨기는 것만으로 서버 데이터 접근을 제한할 수는 없다.

### 실습

체험 로그인 전에 회원 화면이 없는지 확인하고, 로그인 후 이름과 회원 화면을 확인한다. 로그아웃하면 다시 안내 화면이 나타나야 한다. 확장 과제는 사용자 역할에 따라 관리자 버튼을 추가하는 것이다. role 값을 user 객체에 추가하고, 표시 조건을 명시적으로 작성한다.

### 확인 문제와 해설

- Q: Toolbar에 setter를 반드시 그대로 전달해야 하는가? A: 아니다. onLogin 같은 의미가 드러나는 콜백을 전달할 수 있다.
- Q: `user && <p>`에서 user가 null이면 무엇이 나오는가? A: 해당 문단은 렌더링되지 않는다.
- Q: 로그인 상태를 자식 둘이 공유하면 어디에 두는가? A: 가장 가까운 공통 부모를 먼저 검토한다.

## 10. 리스트와 key — AttendanceBook

### 학습 목표

- 배열을 map으로 JSX 배열로 변환한다.
- key가 표시 순서가 아니라 항목의 정체성을 나타냄을 설명한다.
- 검색과 출석 변경을 원본 배열을 수정하지 않고 구현한다.

### 원본 읽기

대상: [AttendanceBook.jsx](https://github.com/soaple/first-met-react-practice-v18/blob/3adbe9bf8a01109abb0b675ace9ae1e0eaf8af41/src/chapter_10/AttendanceBook.jsx).

모듈 상단의 students에는 id와 name을 가진 학생 네 명이 있다. `students.map`은 학생마다 `<li>`를 반환하고, 그 배열이 `<ul>` 안에 들어간다. `key={student.id}`는 올바른 선택이다. 콜백의 두 번째 인자인 index는 선언되어 있으나 사용하지 않는다. 원본은 이름을 출력할 뿐 출석 상태를 저장하거나 변경하지 않는다.

### 이론과 기술

map은 요소를 변환하고 filter는 조건에 맞는 요소를 고른다. 화살표 함수의 본문을 `{}`로 작성하면 명시적인 return이 필요하다. 다음 둘은 같은 결과다.

```jsx
students.map(student => <li key={student.id}>{student.name}</li>);
students.map(student => { return <li key={student.id}>{student.name}</li>; });
```

key는 같은 부모 아래 형제 사이에서 고유하고, 같은 항목에 대해 렌더 사이에 안정적이어야 한다. 재정렬·삽입·삭제되는 목록에 index를 쓰면 위치가 정체성을 대신하게 된다. 렌더 중 Math.random으로 만들면 매번 다른 항목처럼 취급될 수 있다. key는 일반 prop으로 전달되지 않으므로 자식이 id를 사용해야 한다면 별도의 id prop도 준다. [공식 리스트 설명](https://react.dev/learn/rendering-lists).

배열 상태의 한 학생을 바꿀 때는 새 배열과 변경된 학생 객체를 만든다. 원본 객체를 직접 바꾸면 이전 상태와 다음 상태의 경계가 흐려진다.

### 추가 예제와 설명

완성 파일: `examples/src/chapter_10.jsx`. 출석 체크, 이름 검색, 역순 정렬을 추가했다. 핵심 발췌:

```jsx
setStudents(previous => previous.map(student =>
  student.id === id
    ? { ...student, present: !student.present }
    : student
));
```

`...student`는 기존 필드를 복사하고 present만 바꾼다. 검색 결과와 출석 인원은 상태에서 계산한다. 이를 별도 상태로 저장하지 않아 필터 조건 변경과 숫자가 어긋나는 문제를 줄인다. 역순은 `[...previous].reverse()`로 복사본에 적용한다.

### 실습

1. Steve를 체크한다. 출석 인원이 1인지 확인한다.
2. 이름 검색으로 다른 학생을 숨겼다가 검색어를 지운다.
3. 순서를 뒤집고 Steve의 체크가 유지되는지 확인한다.
4. 확장 과제: 삭제 버튼을 추가하고 `filter(student => student.id !== id)`로 처리한다.

주의: 이 예제의 checkbox는 부모 데이터로 제어된다. key를 index로 바꿔도 이 단순 화면만으로 모든 key 문제를 재현하지는 못한다. 차이를 확실히 보려면 행마다 독립적인 편집 상태를 가진 자식 컴포넌트를 만든 뒤 맨 앞 항목을 삭제해 본다.

### 확인 문제와 해설

- Q: 이름을 key로 쓰면 항상 안전한가? A: 동명이인이 있거나 이름이 바뀌면 안전하지 않다. 안정적인 id가 적합하다.
- Q: 정렬하려고 `students.reverse()`를 직접 호출해도 되는가? A: 상태 배열을 직접 수정하므로 복사한 후 처리한다.
- Q: 검색 결과는 왜 state가 아닌가? A: students와 query에서 계산할 수 있는 파생값이기 때문이다.

## 11. 폼 — SignUp

### 학습 목표

- value와 onChange로 텍스트·select를 제어한다.
- checkbox의 checked를 읽고 갱신한다.
- 폼 제출과 입력 검증을 분리한다.

### 원본 읽기

대상: [SignUp.jsx](https://github.com/soaple/first-met-react-practice-v18/blob/3adbe9bf8a01109abb0b675ace9ae1e0eaf8af41/src/chapter_11/SignUp.jsx).

name은 빈 문자열, gender는 ‘남자’로 시작한다. 텍스트 input과 select 모두 value가 상태에 연결된다. 각각의 onChange는 `event.target.value`로 새 문자열을 저장한다. submit 시 이름과 성별을 alert로 출력하고 `preventDefault()`로 브라우저 기본 제출을 막는다. 서버에 회원을 등록하지는 않는다.

원본은 alert 다음에 preventDefault를 호출한다. 추가 예제는 제출 핸들러 첫 줄에서 기본 동작을 취소해 이후 검증의 조기 return과 순서를 단순하게 만든다.

### 이론과 기술

제어 입력은 React 상태가 화면의 값을 결정한다. value를 주면 입력 중 onChange에서 해당 상태를 갱신해야 한다. 문자열 입력은 초기 상태를 `''`로 유지하고 중간에 undefined로 바꾸지 않는다. checkbox는 문자열 value 대신 불리언 checked를 제어한다. label은 입력의 의미를 연결하며 클릭과 보조 기술 사용을 돕는다. [공식 input 설명](https://react.dev/reference/react-dom/components/input).

버튼의 onClick만 처리하면 Enter를 통한 제출 경로를 놓칠 수 있다. `<form onSubmit>`과 `<button type="submit">`으로 제출 경로를 모은다. 예제의 `noValidate`는 브라우저 기본 검증을 생략하고 직접 만든 검증을 보여주기 위한 설정이다.

### 추가 예제와 설명

완성 파일: `examples/src/chapter_11.jsx`. 성별 대신 과정 선택을 사용하고, 안내 확인 checkbox와 오류 메시지를 추가했다.

```jsx
function submit(event) {
  event.preventDefault();
  setResult(null);
  if (!name.trim()) { setError('이름을 입력하세요.'); return; }
  if (!agreed) { setError('실습 안내 확인에 체크하세요.'); return; }
  setError('');
  setResult({ name: name.trim(), course });
}
```

공백만 있는 문자열은 trim 후 빈 값이 된다. 제출할 때만 결과 스냅샷을 저장한다. 입력 편집 중인 name과 제출된 result는 서로 다른 의미이므로 별도로 둔다. 실패한 재제출에서 이전 성공 결과를 지우도록 했다.

```jsx
<input type="checkbox" checked={agreed}
  onChange={event => setAgreed(event.target.checked)} />
```

### 실습

| 입력/행동 | 기대 결과 |
|---|---|
| 이름 비움 + 제출 | 이름 입력 오류 |
| 공백만 입력 + 제출 | 이름 입력 오류 |
| 이름 입력, 안내 미확인 | 안내 확인 오류 |
| 이름·과정·체크 정상 | 제출 정보 표시 |
| 이름 입력 중 Enter | 같은 submit 경로 실행 |

확장 과제: 이메일 필드를 추가하고 오류 메시지를 해당 입력에 연결한다. 브라우저 검증과 사용자 정의 검증 중 어떤 방식을 선택했는지 설명한다. 이 강의의 검증은 프런트엔드 학습용이며, 실제 API에서도 검증이 필요하다.

### 확인 문제와 해설

- Q: checkbox를 `event.target.value`로 처리하면? A: 선택 여부인 불리언을 얻지 못한다. checked를 읽는다.
- Q: preventDefault가 React 상태 갱신도 막는가? A: 아니다. 브라우저 기본 제출 동작을 취소한다.
- Q: 입력할 때 이름을 trim해 저장하면 좋은가? A: 타이핑 중 의도한 공백을 없앨 수 있다. 이 예제는 제출 시 정규화한다.

## 12. 상태 끌어올리기 — Calculator와 TemperatureInput

### 학습 목표

- 두 입력을 동기화하기 위해 가장 가까운 공통 부모에 상태를 둔다.
- 원본 입력과 파생값을 구분한다.
- 잘못된 숫자와 반올림의 경계 조건을 다룬다.

### 원본 읽기

대상: [chapter_12](https://github.com/soaple/first-met-react-practice-v18/tree/3adbe9bf8a01109abb0b675ace9ae1e0eaf8af41/src/chapter_12).

TemperatureInput은 scale 이름을 legend로 보여주고, props.temperature를 표시한다. 입력 이벤트가 발생하면 문자열을 `onTemperatureChange` 콜백으로 부모에 전달한다. 자체 온도 상태는 없다.

Calculator의 temperature는 마지막으로 입력한 문자열이고 scale은 그 입력이 섭씨인지 화씨인지 나타낸다. 섭씨에 입력하면 scale을 c로 바꾸고 화씨를 계산한다. 화씨에 입력하면 반대로 계산한다. BoilingVerdict는 섭씨가 100 이상인지 확인한다.

| 함수 | 책임 |
|---|---|
| toCelsius | `(화씨 - 32) × 5 / 9` |
| toFahrenheit | `섭씨 × 9 / 5 + 32` |
| tryConvert | parseFloat, NaN 검사, 변환, 소수 셋째 자리 반올림 |
| Calculator | 입력 문자열과 입력 단위 소유 |
| TemperatureInput | 표시와 변경 통보 |
| BoilingVerdict | 끓는점 비교 문구 |

### 이론과 기술

함께 변해야 하는 값을 자식마다 독립적으로 저장하면 동기화 규칙이 중복된다. 공유 상태를 공통 부모로 옮기고 자식에 값과 변경 콜백을 전달한다. 이것이 상태 끌어올리기다. 섭씨·화씨·원본 입력을 모두 상태로 저장하기보다 원본과 단위만 저장하고 나머지를 계산한다. [공식 상태 공유 설명](https://react.dev/learn/sharing-state-between-components).

입력값을 문자열로 두면 빈 값과 입력 중 `-` 같은 상태를 보존할 수 있다. 숫자로 너무 일찍 바꾸면 사용자가 입력 중인 형태를 유지하기 어렵다. 변환 함수는 외부 상태를 바꾸지 않는 순수 함수로 분리하면 경계값 검증이 쉽다.

### 원본의 경계 조건

- `parseFloat('12abc')`는 12를 반환하므로 원본은 숫자 접두사를 허용한다.
- 빈 값은 NaN이 되어 변환 결과가 빈 문자열이다.
- 빈 섭씨를 BoilingVerdict에 전달하면 NaN과 100의 비교가 false라 ‘끓지 않습니다’가 나온다. 미입력과 낮은 온도를 구분하지 않는다.
- 반올림된 표시값으로 판정하면 임계값 가까이에서 판정에 영향을 줄 수 있다.

### 추가 예제와 설명

완성 파일: `examples/src/chapter_12.jsx`, `examples/src/temperature.js`.

```jsx
const [input, setInput] = useState({ scale: 'c', text: '' });
const celsius = input.scale === 'c'
  ? input.text : convertText(input.text, toCelsius);
const fahrenheit = input.scale === 'f'
  ? input.text : convertText(input.text, toFahrenheit);
```

단위와 텍스트를 하나의 객체로 바꿔 동시에 갱신한다. 정규식과 Number.isFinite로 유효 입력을 검사한다. 허용 범위는 부호가 있는 정수·소수이며 지수 표기와 Infinity는 학습용 정책으로 거부한다. 빈 값이나 잘못된 값이면 반대편을 비우고 입력 안내를 표시한다. 끓는점 판정은 반올림 전 숫자를 사용한다. 표준 대기압에서의 물을 가정한다.

### 실습

| 입력 | 기대 결과 |
|---|---|
| 섭씨 100 | 화씨 212, 끓는 온도 |
| 화씨 32 | 섭씨 0, 끓는점보다 낮음 |
| 화씨 212 | 섭씨 100, 끓는 온도 |
| 빈 값, `-`, `12abc` | 반대편 빈 값, 유효 입력 안내 |
| 섭씨 99.9999 | 끓는점보다 낮음 |

확장 과제: 길이 변환기를 만든다. m/cm 입력 두 개가 하나의 입력 원본과 단위만 공유하게 한다. 수치 변환과 화면을 분리한다.

### 확인 문제와 해설

- Q: 두 TemperatureInput이 각각 state를 가지면? A: 서로 영향을 주기 위한 동기화 로직이 필요하다. 공통 부모가 단일 원본을 소유하도록 한다.
- Q: parseFloat만으로 전체 입력의 유효성을 검사할 수 있는가? A: 아니다. 숫자 뒤의 잘못된 문자를 무시할 수 있다.
- Q: 변환값을 useEffect에서 state에 저장해야 하는가? A: 이 예제에서는 렌더 중 계산할 수 있어 별도 효과와 상태가 필요하지 않다.

## 13. 컴포넌트 합성 — Card와 ProfileCard

### 학습 목표

- children으로 가변적인 본문을 전달한다.
- 공통 외형과 구체적인 내용의 책임을 분리한다.
- 이름 있는 JSX prop으로 여러 영역을 구성한다.

### 원본 읽기

대상: [chapter_13](https://github.com/soaple/first-met-react-practice-v18/tree/3adbe9bf8a01109abb0b675ace9ae1e0eaf8af41/src/chapter_13).

Card는 title, backgroundColor, children을 받아 둥근 모서리·그림자·여백이 있는 div를 만든다. backgroundColor가 falsy이면 white를 사용한다. title이 있을 때 h1을 출력한 뒤 children을 렌더링한다. ProfileCard는 이름과 배경색을 전달하고 두 문단을 여는 태그와 닫는 태그 사이에 넣는다. 두 문단이 children이다.

Card는 프로필 내용의 문구를 모른다. 외형은 공통화하고 내용은 사용하는 쪽이 작성한다. 함수 인자로 데이터뿐 아니라 JSX도 전달할 수 있다.

### 이론과 기술

합성은 작은 컴포넌트를 조합해 큰 화면을 만드는 방식이다. children은 태그 사이의 JSX를 받는 prop이다. 본문 하나만 필요하면 children이 자연스럽고, header/footer/actions 등 위치가 명확한 영역이 여럿이면 이름 있는 prop을 사용할 수 있다. props는 읽기 전용 입력으로 다룬다. [공식 props·children 설명](https://react.dev/learn/passing-props-to-a-component).

같은 Card를 재사용할 때 문서의 제목 계층을 고려한다. 원본은 카드마다 h1을 사용한다. 추가 예제는 앱의 h1, 챕터의 h2 아래에 들어가므로 h3을 선택했다. 제목 레벨을 무조건 컴포넌트 이름에 고정하지 말고 사용 맥락을 살핀다.

### 추가 예제와 설명

완성 파일: `examples/src/chapter_13.jsx`. footer 슬롯과 저장 버튼을 추가했다. 저장 여부는 사용자가 제공하는 내용에 속하므로 CompositionPractice가 소유한다.

```jsx
<Card title="React 학습 카드"
  footer={<button onClick={() => setSaved(value => !value)}>
    {saved ? '저장 취소' : '저장'}
  </button>}>
  <p>레이아웃은 Card가, 본문과 행동은 사용하는 쪽이 결정합니다.</p>
</Card>
```

Card가 `onSave`, user, course 등 모든 도메인 정보를 알도록 확장하면 재사용 범위가 줄어든다. footer에 이미 구성된 JSX를 주면 Card는 위치만 책임진다. 이 예제의 기본 매개변수 `backgroundColor = 'white'`는 undefined일 때 적용되며 원본의 `|| 'white'`와 모든 경우가 같은 것은 아니다.

### 실습

본문을 목록으로 교체하고 Card의 구현을 바꾸지 않은 채 출력해 본다. footer 버튼을 링크로 교체한다. 확장 과제는 동일한 Card로 프로필·공지·과제 안내를 각각 만드는 것이다.

### 확인 문제와 해설

- Q: children은 항상 문자열인가? A: 아니다. JSX 요소나 여러 요소 등 React가 렌더링할 수 있는 내용을 전달할 수 있다.
- Q: footer 슬롯이 있으면 Card가 저장 상태를 가져야 하는가? A: 아니다. 버튼과 동작을 부모가 구성할 수 있다.
- Q: 모든 prop을 children 하나로 대체하면 좋은가? A: 아니다. 제목·색상 같은 명확한 설정과 가변 본문은 역할이 다르다.

## 14. Context — DarkOrLight

### 학습 목표

- Context 생성, Provider 제공, useContext 소비의 관계를 설명한다.
- props 전달과 Context의 적용 범위를 선택한다.
- Context 값 변경과 렌더링 관계를 이해한다.

### 원본 읽기

대상: [chapter_14](https://github.com/soaple/first-met-react-practice-v18/tree/3adbe9bf8a01109abb0b675ace9ae1e0eaf8af41/src/chapter_14).

ThemeContext.jsx는 기본값 없이 Context를 만들고 DevTools 표시 이름을 지정한다. DarkOrLight가 theme 상태를 소유하며 초기값은 light다. useCallback으로 정의한 toggleTheme는 현재 theme을 비교해 반대 테마로 바꾼다. 의존성 배열이 `[theme]`이므로 theme이 바뀌면 함수 참조도 바뀐다.

Provider는 `{ theme, toggleTheme }`를 제공한다. MainContent는 useContext로 읽고 배경색·글자색·버튼을 구성한다. 원본은 느슨한 비교인 `==`를 쓰지만, 이 강의의 추가 코드는 문자열의 엄격한 비교인 `===`를 사용한다.

```text
DarkOrLight: theme 상태 소유
  └─ ThemeContext.Provider: 값 제공
       └─ MainContent: useContext로 구독
```

### 이론과 기술

Context는 하위 트리에서 값을 읽을 통로다. 실제 상태는 Provider를 렌더링하는 컴포넌트의 useState에 있다. 소비자는 가장 가까운 상위 Provider를 사용한다. Provider가 없으면 createContext의 기본값을 읽는다. 원본처럼 기본값이 없으면 undefined를 구조 분해하다 오류가 날 수 있다. [공식 useContext 설명](https://react.dev/reference/react/useContext).

모든 상태를 Context에 넣을 필요는 없다. 가까운 부모·자식은 props가 단순하고, 깊은 트리에서 여러 소비자가 같은 테마 등을 필요로 할 때 Context를 검토한다. Provider의 객체를 매번 새로 만들면 값의 참조도 바뀐다. useCallback 하나만으로 이 객체까지 안정화되지는 않는다. 성능 문제가 확인되면 책임 분리와 useMemo 등을 검토하고 측정한다.

### 추가 예제와 설명

완성 파일: `examples/src/chapter_14.jsx`. 기본값을 null로 정하고 useTheme 커스텀 Hook에서 Provider 누락을 명확한 오류로 안내한다. Layout은 children만 전달하며 theme prop을 받지 않는다.

```jsx
const ThemeContext = createContext(null);
function useTheme() {
  const value = useContext(ThemeContext);
  if (value === null) throw new Error('ThemeProvider 내부에서 사용하세요.');
  return value;
}
const toggleTheme = () =>
  setTheme(previous => previous === 'light' ? 'dark' : 'light');
```

추가 예제는 작은 화면이라 참조 최적화 코드를 넣지 않았다. 함수형 갱신으로 현재 theme을 클로저에서 읽지 않아도 다음 값을 계산한다. React 18 호환을 위해 `<ThemeContext.Provider value={...}>`를 사용한다.

### 실습

테마를 여러 번 전환하며 글자·배경·버튼 문구가 함께 바뀌는지 확인한다. Layout에 theme 관련 props가 없는지 확인한다. 확장 과제는 같은 Provider 아래에 ThemeBadge를 추가해 현재 테마 이름을 표시하는 것이다. 다른 Provider로 감싼 영역이 독립적으로 동작하는지도 예측한다.

### 확인 문제와 해설

- Q: Context 객체 자체가 theme 상태인가? A: 아니다. 값 전달과 소비에 쓰는 객체이며 상태는 Provider 쪽에 있다.
- Q: useCallback은 함수 실행 결과를 캐시하는가? A: 아니다. 의존성에 따라 함수 참조를 유지한다.
- Q: 중간 Layout에서 useContext를 호출해야 아래 버튼이 읽는가? A: 아니다. 소비자는 자신의 위치에서 가장 가까운 상위 Provider를 읽는다.

## 15. 스타일링 — Blocks와 styled-components

### 학습 목표

- tagged template literal 기반 스타일 정의를 읽는다.
- props로 CSS 값을 계산한다.
- key, 스타일 전용 prop, 반응형 배치를 적용한다.

### 원본 읽기

대상: [Blocks.jsx](https://github.com/soaple/first-met-react-practice-v18/blob/3adbe9bf8a01109abb0b675ace9ae1e0eaf8af41/src/chapter_15/Blocks.jsx).

Wrapper는 flex 컨테이너이고 가로 방향으로 자식을 배치한다. align-items와 justify-content는 각각 교차축과 주축 정렬을 지정한다. Block은 padding과 backgroundColor를 props에서 받아 CSS의 padding과 background-color에 넣는다. blockItems는 label, padding, backgroundColor를 가진 세 항목이다.

map이 반환하는 Block에는 원본 기준 key가 없다. 10장에서 배운 안정적인 key를 여기에도 적용해야 한다. 또한 blockItems의 label은 현재 고유하지만 일반적인 데이터에서는 별도 id를 두는 편이 명확하다.

### 이론과 기술

`styled.div`와 백틱 문자열의 조합은 스타일이 적용된 React 컴포넌트를 만든다. `${props => ...}` 부분은 전달받은 값으로 CSS를 계산한다. 정의는 컴포넌트 함수 바깥에 두어 렌더마다 새 컴포넌트 타입을 만들지 않는다. `$` 접두사가 붙은 transient prop은 스타일 계산용 prop을 DOM 속성으로 전달하지 않게 하는 용도이며 원본 의존성인 v5.3.5에서도 사용할 수 있다. [공식 styled-components API](https://styled-components.com/docs/api).

| 방식 | 특징 | 이 수업에서의 위치 |
|---|---|---|
| 일반 CSS + className | 규칙을 CSS 파일에서 관리 | 앱 공통 스타일 |
| style 객체 | JS 객체로 개별 스타일 지정 | 13장 카드, 14장 테마 |
| styled-components | 컴포넌트와 동적 CSS를 함께 정의 | 15장 블록 |

inline style은 camelCase 속성명과 객체를 사용한다. styled-components 문자열 내부는 `background-color`처럼 CSS 문법을 사용한다. 라이브러리가 있어도 Flexbox의 축·여백·줄바꿈 원리는 동일하게 이해해야 한다.

### 추가 예제와 설명

완성 파일: `examples/src/chapter_15.jsx`. 안정적인 id, transient prop, gap, flex-wrap과 여백 전환 상태를 추가했다. 핵심 발췌:

```jsx
const Block = styled.div`
  padding: ${props => props.$padding};
  background: ${props => props.$backgroundColor};
`;
// map이 반환하는 최상위 요소에 key를 둔다.
<Block key={item.id}
  $padding={compact ? '1rem' : item.padding}
  $backgroundColor={item.color}>{item.label}</Block>
```

배경색은 예제 데이터에서 제공하고 사용자 입력 CSS를 직접 받지 않는다. 좁은 화면에서는 flex-wrap이 줄바꿈을 허용한다. compact 상태는 세 블록에 공통으로 영향을 주지만 CSS 결과 자체를 state에 저장하지는 않는다.

### 실습

원본의 padding 1rem, 3rem, 2rem이 크기에 주는 영향을 예측한다. 추가 예제에서 여백을 바꾸고 브라우저 폭을 줄인다. 확장 과제는 선택한 블록에 테두리를 강조하는 기능이다. selectedId 상태를 부모에 두고 `$selected` prop으로 테두리를 계산한다.

### 확인 문제와 해설

- Q: `$padding`의 `$`는 CSS 문법인가? A: 아니다. styled-components의 스타일 전용 prop 관례와 기능이다.
- Q: map 안의 Block에 key가 필요한가? A: 그렇다. styled 컴포넌트도 React 컴포넌트이므로 같은 규칙을 따른다.
- Q: padding이 다른데 align-items가 flex-start라면? A: 블록 위쪽은 맞지만 아래쪽 높이는 달라질 수 있다.

## 16. 학습 마무리와 다음 구현

8장은 이벤트가 상태를 바꾸는 출발점이다. 9장은 그 상태로 화면을 선택하고, 10장은 여러 항목을 안정적으로 표시한다. 11장은 입력을 상태로 관리하고, 12장은 공유할 상태의 위치를 결정한다. 13장은 화면 구조를 재사용하고, 14장은 깊은 트리에 공통 값을 제공하며, 15장은 상태와 데이터를 스타일에 연결한다.

- 이벤트 핸들러가 언제 실행되는지 말할 수 있다.
