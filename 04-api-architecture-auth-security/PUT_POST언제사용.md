# PUT과 POST를 언제 사용하면 좋은가?

**일반적인 회원 가입은 `POST` 요청을 사용하는 것이 정석이자 가장 좋은 선택**입니다.

그 이유는 회원 가입 프로세스의 특성과 HTTP 메서드의 설계 철학이 정확히 맞아떨어지기 때문입니다. 그 이유와 예외적인 경우를 비교해 드리겠습니다.

---

### 1. 회원 가입에 `POST`가 적합한 이유 (권장)

* **서버가 식별자를 생성 (Auto Increment / UUID):**
회원 가입을 할 때 사용자가 자신의 아이디(PK)를 직접 만드는 경우도 있지만, 대개의 경우 시스템이 내부적으로 자동 증가하는 순번(`id: 1, 2, 3...`)이나 고유 ID(UUID)를 발급하여 데이터베이스에 저장합니다.
* **비멱등성 (Non-idempotent):**
`POST`는 "이 데이터를 새로 등록해 줘"라는 의미입니다. 네트워크 불안정 등으로 인해 사용자가 '회원가입' 버튼을 두 번 연속 클릭했을 때, `POST`를 쓰면 서버가 각각의 요청을 별개의 생성 요청으로 받아들여 자칫 중복 가입 에러를 내거나 안전하게 막아낼 수 있습니다. (반면 멱등성이 보장되어야 하는 PUT은 중복 요청 시 오작동을 유발할 수 있습니다.)

### 2. 그렇다면 `PUT`을 회원 가입에 쓸 수 있는 경우는?

`PUT`을 회원 가입에 쓰려면 **클라이언트가 생성될 리소스의 고유 식별자(PK 또는 URI)를 완벽하게 미리 알고 지정**할 수 있어야 합니다.

* **예시 (이메일이나 소셜 ID를 PK로 쓰는 경우):**
만약 회원 가입 엔드포인트가 `/users/simpleego@gmail.com` 처럼 이메일 주소 자체를 식별자로 사용하고, 클라이언트가 이 주소를 확정하여 "이 주소로 계정을 만들어(또는 덮어씌워) 줘"라고 요청한다면 `PUT`을 사용할 수 있습니다.
* **특징:** 이 경우 동일한 이메일로 `PUT`을 10번 보내도 결과는 항상 "해당 이메일을 가진 계정 1개가 존재함"으로 유지되므로 **멱등성**이 성립합니다.

---

### 요약 비교

| 구분 | `POST /users` (권장) | `PUT /users/{id}` (조건부 가능) |
| --- | --- | --- |
| **리소스 식별자 결정** | 서버가 결정 (Auto Increment 등) | 클라이언트가 사전에 결정 (이메일, 커스텀 ID 등) |
| **SQL 매핑** | `INSERT` | `INSERT` 또는 `UPSERT` (`INSERT ... ON DUPLICATE KEY UPDATE`) |
| **멱등성 여부** | ❌ 아니오 (여러 번 보내면 중복 발생 가능) | 영 예 (여러 번 보내도 최종 상태 동일) |
| **적합한 상황** | 일반적인 회원 가입 | 이미 존재하는지 여부를 확신하며 클라이언트가 ID를 통제하는 경우 |

대다수의 프레임워크와 API 설계 지침(RESTful API 디자인)에서도 새로운 자원을 생성하는 회원 가입 API는 **`POST /users` 또는 `POST /auth/signup**` 형태로 구현하는 것을 표준으로 삼고 있습니다.
