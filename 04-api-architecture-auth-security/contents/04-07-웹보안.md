# 풀스택 웹 보안 핵심 및 실습 가이드

대상: AX 풀스택 빌더 과정 · 비전공자 중심 · FastAPI + React + PostgreSQL/MariaDB

2차 프로젝트를 수행하기 전에 웹 보안을 전문적으로 깊이 학습할 필요는 없습니다. 다만 클라이언트가 요청을 보내고, 서버가 처리한 결과를 반환하는 과정에서 어떤 보안 문제가 발생하고 어떻게 방어하는지는 반드시 이해해야 합니다.

특히 AI 에이전트가 코드를 생성하더라도 개발자는 보안 요구사항을 제시하고, 생성된 코드가 안전한지 검증할 수 있어야 합니다.

## 1. 웹 요청부터 응답까지의 보안 구조

요청은 각 보안 단계를 통과하고, 응답은 필요한 데이터만 안전하게 전달합니다.

핵심 원칙은 다음과 같습니다.

클라이언트는 신뢰하지 않는다. 모든 중요한 검증과 권한 판단은 서버에서 다시 수행한다.

예를 들어 React에서 가격을 10,000원으로 표시해도 사용자가 개발자 도구를 이용해 100원으로 변경하여 전송할 수 있습니다. 따라서 서버는 DB에 저장된 상품 가격을 기준으로 주문 금액을 계산해야 합니다.

## 4. 핵심 보안 실습

### 실습 1. 클라이언트 입력값 검증 — Pydantic

필수 실습

상황: 사용자가 상품 가격을 음수로 입력하거나 수량을 1,000,000개로 조작하여 요청하는 경우

FastAPI에서는 Pydantic으로 서버가 허용할 데이터 범위를 제한할 수 있습니다.

main.py

```
from fastapi import FastAPIfrom pydantic import BaseModel, Fieldapp = FastAPI()class Order(BaseModel):    product_id: int = Field(gt=0)    quantity: int = Field(ge=1, le=10)@app.post("/orders")def create_order(order: Order):    return {        "message": "주문 요청 검증 완료",        "data": order.model_dump()    }
```

FastAPI 실행:

```
pip install fastapi uvicorn
uvicorn main:app --reload
```

`http://127.0.0.1:8000/docs`에서 직접 요청을 전송합니다.

정상 요청:

```
{"product_id": 1, "quantity": 2}
```

비정상 요청:

```
{"product_id": 1, "quantity": -5}
```

예상 결과

422 Unprocessable Content

수량이 허용 범위를 벗어나므로 FastAPI가 요청을 거부합니다.

학습 포인트: 프론트엔드 검증은 사용자 편의성을 높이고, 백엔드 검증은 데이터 무결성을 보호합니다. 주문 가격처럼 중요한 데이터는 요청 값을 그대로 믿지 않고 DB에서 조회해야 합니다.

### 실습 2. SQL Injection 방어

필수 실습

상황: 로그인이나 검색 기능에 입력한 문자열이 SQL 문장의 일부로 해석되는 경우

위험한 방식

문자열을 SQL에 직접 연결

SQL 구조가 변조될 수 있음

안전한 방식

파라미터 바인딩 사용

입력값을 데이터로 처리

위험한 SQL 작성 방법 (실행하지 않고 비교)

```
sql = f"SELECT * FROM users WHERE name = '{name}'"
```

안전한 방법 (SQLAlchemy)

```
from sqlalchemy import textsql = text(    "SELECT * FROM users WHERE name = :name")result = session.execute(    sql,    {"name": name})
```

실습에서는 검색어에 다음을 입력해 봅니다.

```
' OR '1'='1
```

문자열 결합 방식에서는 SQL의 조건이 변형될 수 있습니다. 반면 파라미터 바인딩 방식에서는 입력값 전체를 하나의 문자열 데이터로 취급합니다.&#x20;

### 실습 3. XSS(Cross-Site Scripting) 방어

필수 실습

상황: 사용자가 게시글이나 댓글에 HTML 또는 JavaScript를 포함하여 다른 사용자의 브라우저에서 실행되도록 유도하는 경우

HTML + JavaScript 실습

```

<input id="message" value="<b>안녕하세요</b>">
<button onclick="renderUnsafe()">위험한 출력</button>
<button onclick="renderSafe()">안전한 출력</button>

<div id="result"></div>

<script>
function renderUnsafe() {
  const value = document.querySelector("#message").value;
  document.querySelector("#result").innerHTML = value;
}

function renderSafe() {
  const value = document.querySelector("#message").value;
  document.querySelector("#result").textContent = value;
}
</script>

```

실습 방법: `<b>안녕하세요</b>`를 입력하고 두 버튼을 각각 클릭해 비교합니다.

- `innerHTML`: HTML 태그를 해석하여 글자를 굵게 출력
- `textContent`: 태그를 실행하지 않고 문자열 그대로 출력

실제 XSS 위험은 공격자가 입력한 이벤트 핸들러 등의 코드가 실행될 때 발생합니다. 이 예제는 HTML 해석 여부를 안전하게 비교하는 기초 실습입니다.

React에서도 일반적인 `{message}` 출력은 기본적으로 이스케이프 처리됩니다. 단, `dangerouslySetInnerHTML`은 별도의 HTML 정제 없이 사용하지 않아야 합니다.

### 실습 4. JWT 인증과 접근 제어

필수 실습

상황: 로그인하지 않은 사용자가 `/mypage` API를 직접 호출하는 경우

JWT는 로그인 성공 후 발급하는 서명된 토큰입니다. 서버는 토큰의 서명과 만료시간 등을 검증하여 사용자를 식별할 수 있습니다. JWT의 페이로드 자체는 암호화되지 않습니다.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://fastapi.tiangolo.com\&sz=32)

FastAPI



여기서는 실제 로그인 전체를 구현하기보다 토큰이 없거나 잘못되면 API를 사용할 수 없는지 확인합니다.

설치:

```
pip install PyJWT
```

auth_demo.py

```
from fastapi import FastAPI, Depends, HTTPExceptionfrom fastapi.security import HTTPBearer, HTTPAuthorizationCredentialsimport jwtimport osapp = FastAPI()security = HTTPBearer(auto_error=False)# 환경변수에 충분히 긴 무작위 비밀키 설정SECRET = os.environ["JWT_SECRET"]ALGORITHM = "HS256"def check_token(    credentials: HTTPAuthorizationCredentials | None = Depends(security)):    if credentials is None:        raise HTTPException(401, "로그인이 필요합니다.")    try:        payload = jwt.decode(            credentials.credentials,            SECRET,            algorithms=[ALGORITHM],            options={"require": ["exp", "sub"]}        )        return payload["sub"]    except jwt.InvalidTokenError:        raise HTTPException(401, "유효하지 않은 토큰입니다.")@app.get("/mypage")def mypage(username: str = Depends(check_token)):    return {"message": f"{username}님의 마이페이지"}
```

Windows PowerShell에서 실습용 비밀키 설정:

```
$env:JWT_SECRET = python -c "import secrets; print(secrets.token_urlsafe(32))"
uvicorn auth_demo:app --reload
```

`http://127.0.0.1:8000/docs`에서 `/mypage`를 실행합니다.

| 요청 상황          | 예상 결과            |
| -------------- | ---------------- |
| 토큰 없이 요청       | 401 Unauthorized |
| 잘못된 토큰 전송      | 401 Unauthorized |
| 서버가 발급한 유효한 토큰 | 200 OK           |

이 예제는 JWT 검증 부분만 분리한 것입니다. 정상 토큰 발급은 다음 통합 실습에서 구현하도록 하면 좋습니다.

추가로 설명할 개념

- 인증: 내가 누구인지 확인
- 인가: 내가 해당 작업을 수행할 권한이 있는지 확인
- 401: 인증되지 않았거나 인증정보가 유효하지 않음
- 403: 인증된 사용자에게 해당 작업 권한이 없음

특히 관리자의 API는 React에서 관리자 버튼을 숨기는 것만으로 보호할 수 없습니다. FastAPI에서 반드시 권한을 재검사해야 합니다.

### 실습 5. CORS 보안 설정

상황: React는 `localhost:5173`, FastAPI는 `localhost:8000`에서 실행하는 경우

CORS는 서로 다른 출처 간 브라우저의 응답 접근을 제어하는 정책입니다.

FastAPI 설정

```
from fastapi.middleware.cors import CORSMiddlewareapp.add_middleware(    CORSMiddleware,    allow_origins=["http://localhost:5173"],    allow_credentials=False,    allow_methods=["GET", "POST"],    allow_headers=["Content-Type", "Authorization"],)
```

실습은 `allow_origins`에 허용한 주소와 허용하지 않은 주소에서 브라우저 `fetch()`를 실행해 비교합니다.

주의: CORS는 인증·인가를 대신하는 보안 장치가 아닙니다. Postman이나 Python 요청은 브라우저의 CORS 정책에 의해 제한되지 않습니다.

### 실습 6. 오류 처리와 민감정보 보호

상황: DB 연결 오류가 발생하여 사용자에게 내부 DB 주소, SQL 문장, 서버 경로가 노출되는 경우

```
import loggingfrom fastapi import HTTPExceptionlogger = logging.getLogger(__name__)@app.get("/products")def get_products():    try:        # 예시: DB 조회 시 발생한 오류        raise ConnectionError("DB 연결 실패")    except Exception:        logger.exception("상품 조회 중 오류 발생")        raise HTTPException(            status_code=500,            detail="서버 처리 중 오류가 발생했습니다."        )
```

이 코드는 오류 노출 차이를 확인하기 위한 단독 예제입니다.

서버 로그에는 원인 분석에 필요한 정보를 남기되, 사용자에게는 내부 기술정보를 반환하지 않습니다. 로그에도 비밀번호, JWT, 개인정보가 기록되지 않도록 주의해야 합니다.

## 5. 나머지 필수 보안 설정

다음 항목들은 코드 작성보다 설정을 직접 확인하는 실습으로 진행하면 효율적입니다.

| 보안 항목      | 실습 내용                       | 핵심 확인 사항                    |
| ---------- | --------------------------- | --------------------------- |
| HTTPS      | 개발자 도구 Network에서 요청 프로토콜 확인 | 배포 환경에서는 HTTPS 적용           |
| CSRF       | 쿠키 기반 로그인에서 CSRF 토큰 유무 비교   | 쿠키 인증 시 SameSite·CSRF 방어 적용 |
| 비밀번호       | `pwdlib[argon2]`로 해시 및 검증   | 평문 비밀번호 DB 저장 금지            |
| 환경변수       | `.env`에 DB 비밀번호와 JWT 키 분리   | `.gitignore`로 Git 커밋 제외     |
| Rate Limit | 로그인 API를 반복 호출하여 429 확인     | 반복적인 인증 시도 제한               |
| 보안 헤더      | 응답의 보안 헤더 확인                | CSP, HSTS 등 배포 환경에 맞게 설정    |
| 의존성 점검     | `pip-audit` 실행              | 취약한 라이브러리 확인                |

인증 설계에서 특히 구분해야 할 점이 있습니다. JWT를 `Authorization` 헤더에 직접 넣는 방식과 쿠키로 자동 전송하는 방식은 보안 고려사항이 다릅니다. 쿠키 기반 인증에서는 CSRF 방어가 중요하며, JWT 저장 위치에 따라 XSS 위험도 달라집니다.

### 최소 API 설계

| Method | URI              | 보안 적용                  |
| ------ | ---------------- | ---------------------- |
| POST   | `/auth/register` | 입력 검증, 비밀번호 해시         |
| POST   | `/auth/login`    | 비밀번호 확인, JWT 발급, 요청 제한 |
| GET    | `/todos`         | JWT 검증, 본인 데이터만 조회     |
| POST   | `/todos`         | JWT 검증, 입력 검증          |
| PUT    | `/todos/{id}`    | JWT 검증, 소유권 확인         |
| DELETE | `/todos/{id}`    | JWT 검증, 소유권 확인         |

여기서 가장 중요한 실습은 다른 사용자의 TODO를 수정하거나 삭제하려고 시도하는 것입니다.

사용자 A가 로그인한 상태에서 사용자 B의 TODO ID로 요청하더라도 서버는 소유권 검증으로 접근을 차단해야 합니다.

```
# 사용자별 TODO 접근 검사의 핵심 조건todo = session.query(Todo).filter(    Todo.id == todo_id,    Todo.user_id == current_user.id).first()if not todo:    raise HTTPException(        status_code=404,        detail="TODO를 찾을 수 없습니다."    )
```

존재하지 않는 TODO와 접근 권한이 없는 TODO에 모두 404를 반환하면 타인의 데이터 존재 여부 노출을 줄일 수 있습니다.

## 7. 학생용 보안 테스트 체크리스트

프로젝트를 완성한 후 아래 항목을 직접 확인하고 테스트 결과를 기록하도록 합니다.

보안 점검 진행률

0 / 10

인증

인가

접근 통제

음수 수량 등 잘못된 입력을 서버가 거부한다.

입력 검증

SQL Injection

게시글의 HTML 문자열을 실행하지 않고 출력한다.

## 8. AI 에이전트 시대에 개발자가 담당할 보안 역할

2차 프로젝트에서는 AI가 코드를 만들어도 개발자가 보안 요구사항과 테스트 기준을 명확히 제시하도록 교육해야 합니다.

| 단계  | 개발자가 할 일              | AI에 맡길 일         |
| --- | --------------------- | ---------------- |
| 설계  | 인증 방식, 접근 권한 정책 결정    | 보안 설계 초안 작성      |
| 구현  | 보안 요구사항과 검증 기준 제공     | 인증·검증 코드 생성      |
| 테스트 | 공격 상황 및 합격 기준 정의      | pytest 보안 테스트 작성 |
| 검토  | 실제 권한 우회, 정보 노출 확인    | 코드 취약점 분석 보조     |
| 배포  | 비밀키·HTTPS·DB 접근 범위 검증 | 배포 설정 및 체크리스트 초안 |

특히 AI 에이전트가 기능 구현을 완료했다고 보고하더라도, 개발자가 직접 미인증 요청, 타인 데이터 접근, 잘못된 입력, SQL Injection, XSS 테스트를 진행하도록 해야 합니다.

이는 2차 프로젝트뿐 아니라 이후 AI 에이전트 기반의 3차 기업 프로젝트에서도 동일하게 적용할 수 있는 개발 습관입니다.

## 최종 교육 방향

2차 프로젝트 전에는 웹 보안의 수많은 공격 기법을 암기시키기보다 다음 세 가지 원칙을 이해하도록 하는 것이 중요합니다.

1. 클라이언트의 모든 요청은 조작될 수 있다. 따라서 서버에서 다시 검증한다.
2. 로그인 여부와 접근 권한은 다르다. 인증된 사용자라도 타인의 정보에 접근할 수 없어야 한다.
3. 정상 동작뿐 아니라 비정상 요청도 테스트한다. AI가 만든 코드 역시 보안 검증을 통과해야 한다.

8시간 동안 이 원칙들을 TODO API 하나로 직접 경험하게 한 후 2차 프로젝트를 시작하는 구성이 적절하다고 판단합니다.
