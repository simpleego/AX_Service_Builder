# CSRF와 XSS 완벽 이해: 비유부터 실제 공격 과정과 방어 코드까지

웹 개발에서 CSRF와 XSS는 반드시 이해해야 하는 대표적인 웹 보안 공격입니다.

두 공격 모두 웹 브라우저를 이용하지만, 공격자가 악용하는 대상과 공격 방식은 완전히 다릅니다.

가장 쉽게 구분하면 다음과 같습니다.

- CSRF: 공격자가 사용자의 권한을 악용하여 사용자가 원하지 않는 요청을 서버에 보내도록 만드는 공격
- XSS: 공격자가 웹페이지에 악성 JavaScript를 삽입하여 다른 사용자의 브라우저에서 실행되도록 만드는 공격

먼저 일상생활의 비유로 이해한 다음, 실제 React와 FastAPI 환경에서는 어떤 문제가 발생하고 어떻게 방어하는지 설명하겠습니다.

## 1. CSRF: 다른 사람이 내 이름으로 업무를 처리하도록 만드는 공격

### 비유: 은행 직원이 도장만 확인하는 상황

어떤 은행이 고객의 업무를 처리할 때 다음 규칙을 사용한다고 가정하겠습니다.

> "고객의 도장이 찍혀 있으면 본인이 요청한 것으로 인정한다."

그런데 공격자가 은행 고객의 도장을 직접 훔치지 않고도, 고객이 모르는 사이에 해당 도장이 찍힌 송금 서류를 은행에 제출하도록 만들었다면 어떻게 될까요?

은행 직원은 도장을 확인하고 송금을 처리합니다.

문제는 도장은 진짜이지만, 송금을 요청한 사람의 의도는 가짜라는 것입니다.

웹에서는 로그인 세션 쿠키가 도장과 유사한 역할을 합니다.

CSRF 공격 과정 — 은행 송금 예시

서버가 세션 쿠키만으로 요청을 신뢰하면, 사용자가 의도하지 않은 작업이 실행될 수 있습니다.

### 실제 웹사이트에서는 어떻게 발생할까?

사용자가 은행 사이트 `https://bank.example`에 로그인했다고 가정하겠습니다.

1단계. 정상 로그인

은행 서버는 로그인에 성공한 사용자에게 세션 쿠키를 발급합니다.

```
Set-Cookie: session_id=abc123; HttpOnly; Secure
```

브라우저는 해당 쿠키를 저장하고, 이후 조건에 맞는 은행 서버 요청에 자동으로 첨부합니다.

2단계. 사용자가 악성 사이트 방문

사용자가 로그아웃하지 않은 상태에서 공격자가 만든 웹사이트를 방문합니다.

그 사이트에는 다음과 같은 코드가 숨겨져 있을 수 있습니다.

```
<form
  action="https://bank.example/transfer"
  method="POST"
>
  <input name="to" value="attacker">
  <input name="amount" value="1000000">
</form>

<script>
  document.forms[0].submit();
</script>
```

이 코드는 페이지가 열리면 은행 서버로 송금 요청을 시도합니다.

3단계. 브라우저가 요청 전송

해당 요청에 은행 세션 쿠키가 첨부될 수 있는 환경이라면 서버는 로그인된 사용자의 요청으로 인식할 수 있습니다.

4단계. 은행 서버가 송금 처리

은행 서버가 세션 쿠키만 확인한다면, 사용자의 명시적인 동의가 없는 송금 요청까지 처리할 위험이 있습니다.

단, 위 사례가 실제로 성공하려면 쿠키의 `SameSite` 설정, 브라우저 정책, 서버의 요청 검증 방식 등이 공격을 허용해야 합니다. 현대 브라우저의 기본적인 쿠키 보호 기능은 이런 공격의 상당 부분을 제한합니다.

### CSRF의 핵심 문제

서버는 다음 두 가지를 혼동한 것입니다.

- 인증(Authentication): 로그인한 사용자가 누구인가?
- 요청의 정당성: 해당 사용자가 실제로 이 작업을 의도했는가?

즉, 로그인되어 있다는 사실만으로 모든 요청을 신뢰해서는 안 됩니다.

## 2. XSS: 게시판에 악성 코드를 숨겨 다른 사람의 컴퓨터에서 실행하는 공격

### 비유: 게시판 공지문에 위험한 명령을 숨긴 상황

학교 게시판에 누구나 글을 붙일 수 있다고 가정하겠습니다.

정상적인 게시글은 다음과 같습니다.

> "내일 오전 10시에 강의가 시작됩니다."

그런데 누군가 다음과 같은 글을 올렸습니다.

> "이 글을 읽는 사람은 자동으로 자신의 개인정보를 특정 주소로 보내라."

현실의 게시판에서는 단순히 글을 읽는다고 명령이 실행되지는 않습니다.

하지만 웹 브라우저는 특정 HTML과 JavaScript를 문서의 일부가 아니라 실행할 코드로 해석할 수 있습니다.

이 점을 공격자가 악용하는 것이 XSS입니다.

XSS 공격 과정 — 게시판 댓글 예시

서버에 저장된 악성 코드가 다른 사용자의 브라우저에서 실행되는 저장형 XSS의 예시입니다.

### 실제 웹사이트에서 발생하는 과정

1단계. 공격자가 악성 댓글 작성

다음과 같은 문자열을 댓글에 입력했다고 가정합니다.

```
<script>alert("XSS 공격 성공!")</script>
```

여기서는 위험성을 쉽게 보여주기 위해 경고창만 띄우는 예제를 사용했습니다.

2단계. 서버가 입력값을 저장

게시판 서버가 문자열을 데이터베이스에 그대로 저장합니다.

문자열 저장 자체가 반드시 취약점인 것은 아닙니다.

문제는 나중에 해당 문자열을 화면에 출력하는 방법입니다.

3단계. 다른 사용자가 게시글 열람

서버가 댓글을 HTML 문서에 별도의 이스케이프 처리 없이 삽입했다고 가정하겠습니다.

```
<div class="comment">
  <script>alert("XSS 공격 성공!")</script>
</div>
```

4단계. 브라우저에서 JavaScript 실행

브라우저가 해당 스크립트를 실행하면 경고창이 나타납니다.

실제 공격에서는 경고창 표시보다 훨씬 심각한 문제가 발생할 수 있습니다.

- 사용자가 입력하는 정보 탈취
- 웹페이지 내용 위조
- 로그인된 사용자 권한을 이용한 API 요청
- 사용자를 가짜 로그인 화면으로 유도

특히 XSS는 악성 코드가 취약한 웹사이트의 실행 문맥에서 동작한다는 점이 위험합니다.

이것이 CSRF와 XSS의 결정적인 차이입니다.

CSRF는 사용자의 권한을 이용해 외부에서 요청을 유도하는 공격이고, XSS는 신뢰받는 웹페이지 내부에서 악성 JavaScript가 실행되는 공격입니다.

## 3. CSRF를 방어하는 방법

CSRF 방어는 다음 질문에서 시작합니다.

"이 요청이 로그인된 사용자에게서 왔다는 것뿐 아니라, 정상적인 웹 애플리케이션에서 생성된 요청인지 어떻게 확인할까?"

### ① CSRF 토큰: 은행 거래에 일회용 확인번호를 추가하는 방법

은행에서 송금할 때 도장 외에 별도의 확인번호를 요구한다면 어떨까요?

공격자는 로그인 세션을 악용하여 송금 요청을 유도할 수 있더라도, 정상적인 사용자의 확인번호를 알지 못하면 거래를 완료할 수 없습니다.

CSRF 토큰도 비슷합니다.

CSRF 토큰 검증 과정

서버가 로그인 세션별 CSRF 토큰 생성

예시: `csrf_token = "x7k92..."`

정상 웹페이지에 토큰 전달

사용자가 송금 요청 시 토큰도 함께 전송

서버에서 세션과 토큰 일치 여부 검사

정상 토큰

요청 처리

토큰 없음 / 불일치

403 Forbidden

React에서 요청을 보낼 때는 다음과 같이 사용할 수 있습니다.

```
async function transferMoney() {
  await fetch("/api/transfer", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "X-CSRF-Token": csrfToken
    },
    credentials: "same-origin",
    body: JSON.stringify({
      to: "user02",
      amount: 10000
    })
  });
}
```

여기서 중요한 부분은 `X-CSRF-Token`입니다.

서버는 단순히 토큰이 존재하는지만 검사하는 것이 아니라, 로그인 세션에 연결된 정상적인 토큰인지 검증해야 합니다. 서버에서 안전하게 생성하고 검증하는 과정이 반드시 필요합니다.

### ② Same-Origin Policy와 SameSite 쿠키

이 두 기술은 이름이 비슷하지만 기능이 다릅니다.

| 기술                 | 주요 기능                        |
| ------------------ | ---------------------------- |
| Same-Origin Policy | 다른 출처의 응답이나 데이터에 대한 접근을 제한   |
| SameSite 쿠키        | 다른 사이트에서 발생한 요청에 쿠키를 첨부할지 제어 |
| Origin 검증          | 서버가 요청의 출처를 확인해 허용 여부 결정     |

특히 입문자가 기억해야 할 것은 Same-Origin Policy만으로 CSRF를 완전히 막을 수 없다는 점입니다.

다른 사이트가 은행 서버의 응답을 읽지 못하더라도, 요청 자체는 특정 방식으로 전송할 수 있기 때문입니다.

따라서 쿠키에 다음과 같은 옵션을 적용할 수 있습니다.

```
Set-Cookie: session_id=abc123;
            HttpOnly;
            Secure;
            SameSite=Lax
```

`SameSite=Lax`는 많은 교차 사이트 요청에서 쿠키 전송을 제한하며, `Strict`는 더 강하게 제한합니다. 다만 예외와 제약이 있으므로 CSRF 토큰 및 서버 측 검증과 함께 사용하는 것이 안전합니다.&#x20;

### ③ 중요 작업에 재인증 적용

송금, 비밀번호 변경, 계정 탈퇴 등은 정상적으로 로그인했더라도 비밀번호 재입력이나 추가 인증을 요구할 수 있습니다.

이는 CSRF뿐 아니라 세션을 악용한 다른 공격의 피해를 줄이는 데도 도움이 됩니다.

## 4. XSS를 방어하는 방법

XSS 방어에서 가장 중요한 질문은 다음과 같습니다.

"사용자가 입력한 데이터를 브라우저가 JavaScript 코드로 실행하지 않고, 단순한 문자로 표시하도록 하려면 어떻게 해야 할까?"

### ① 이스케이프 처리: 위험한 문자를 일반 문자로 표시

React에서 아래처럼 데이터를 출력한다고 가정하겠습니다.

```
function Comment({ content }) {
  return <div>{content}</div>;
}
```

사용자가 다음 문자열을 입력했다고 해도,

```
<script>alert("공격!")</script>
```

React는 일반적인 JSX 텍스트 표현식에서 이를 자동으로 이스케이프하여 실행 가능한 HTML이 아니라 텍스트로 처리합니다.

그렇다면 위험한 코드는 무엇일까요?

```
function Comment({ content }) {
  return (
    <div
      dangerouslySetInnerHTML={{
        __html: content
      }}
    />
  );
}
```

`dangerouslySetInnerHTML`은 전달한 문자열을 HTML로 해석하게 합니다.

여기에 검증되지 않은 HTML을 넣으면 XSS 취약점이 생길 수 있습니다. 단순히 `<script>` 태그만 제거해서 해결되는 것도 아닙니다. 이벤트 핸들러나 위험한 URL 등 다른 실행 경로도 존재합니다.

따라서 일반 텍스트라면 JSX 표현식으로 출력하고, HTML 자체를 허용해야 한다면 신뢰할 수 있는 HTML 정화(Sanitization) 라이브러리와 적절한 정책을 사용해야 합니다.&#x20;

### ② CSP: 허가받은 스크립트만 실행시키는 경비원

CSP(Content Security Policy)는 웹사이트에서 어떤 출처의 스크립트와 리소스를 실행하거나 불러올 수 있는지 제한하는 보안 정책입니다.

비유하면 건물에 들어올 수 있는 사람을 관리하는 출입 통제 시스템과 같습니다.

서버가 다음과 같은 헤더를 응답에 포함할 수 있습니다.

```
Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  object-src 'none';
  base-uri 'self'
```

주요 의미는 다음과 같습니다.

| 설정                   | 의미                  |
| -------------------- | ------------------- |
| `default-src 'self'` | 기본적으로 같은 출처의 리소스 허용 |
| `script-src 'self'`  | 같은 출처의 스크립트만 허용     |
| `object-src 'none'`  | 플러그인 기반 콘텐츠 차단      |
| `base-uri 'self'`    | 문서의 기준 URL 출처 제한    |

위 정책에서는 일반적인 인라인 스크립트 실행도 제한됩니다.

그러나 CSP는 XSS를 막는 유일한 방어책이 아닙니다. 안전한 출력 처리와 함께 사용해야 하며 실제 서비스에서는 사용하는 스크립트에 맞게 정책을 구성해야 합니다.

### ③ HttpOnly 쿠키: JavaScript가 쿠키를 읽지 못하도록 보호

로그인 세션 쿠키에 `HttpOnly`를 설정하면 브라우저의 JavaScript에서 해당 쿠키를 `document.cookie`로 읽을 수 없습니다.

예를 들어 다음과 같습니다.

```
Set-Cookie: session_id=abc123;
            HttpOnly;
            Secure;
            SameSite=Lax
```

하지만 중요한 제약이 있습니다.

HttpOnly는 XSS 자체를 방지하지 않습니다.

악성 JavaScript가 실행된 경우 쿠키 값을 직접 읽지 못하더라도, 사용자의 권한으로 서버에 요청을 보내는 공격은 여전히 가능할 수 있습니다.

따라서 HttpOnly는 XSS 피해를 줄이는 방어책이지 XSS 자체의 해결책은 아닙니다.

## 5. CSRF와 XSS의 차이 한눈에 비교

| 구분         | CSRF                         | XSS                  |
| ---------- | ---------------------------- | -------------------- |
| 핵심 개념      | 사용자를 속여 요청하게 만듦              | 브라우저에서 악성 코드 실행      |
| 주요 악용 대상   | 로그인 세션과 사용자 권한               | 브라우저의 스크립트 실행 문맥     |
| 공격 사례      | 몰래 송금 요청                     | 악성 댓글로 스크립트 실행       |

## 7. 입문 개발자를 위한 최종 정리

강의에서는 두 가지 질문으로 구분하도록 설명하면 효과적입니다.

CSRF: "누가 이 요청을 하도록 만들었는가?"

정상적으로 로그인한 사용자의 브라우저에서 요청이 왔다고 해도 실제 사용자가 의도한 요청이 아닐 수 있습니다. 따라서 요청의 출처와 CSRF 토큰 등을 확인해야 합니다.

XSS: "이 데이터가 단순한 글자인가, 실행되는 코드인가?"

사용자가 입력한 문자열이 악성 JavaScript로 해석되지 않도록 출력 시 안전하게 처리해야 합니다.

한 가지 더 중요한 사실은 XSS 취약점이 존재하면 CSRF 방어까지 우회될 수 있다는 것입니다. 악성 스크립트가 정상 웹사이트 내부에서 실행되면 해당 사이트의 CSRF 토큰을 이용해 요청을 보내는 상황도 가능하기 때문입니다.

따라서 React와 FastAPI를 함께 사용하는 프로젝트에서는 CSRF와 XSS를 개별적으로 방어하되, 두 보안 대책이 서로 연결되어 있다는 점까지 이해하는 것이 중요합니다.
