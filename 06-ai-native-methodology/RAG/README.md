# RAG 문서 청킹 전략

**청킹(Chunking)은 문서를 검색에 사용할 단위로 나누는 작업**입니다. 일반적인 벡터 검색 RAG에서는 각 청크를 임베딩하고, 질문과 유사한 청크를 찾아 LLM에 전달합니다. 따라서 청크를 설계할 때는 **질문과 관련된 부분이 잘 검색되는지**, 그리고 **찾아낸 부분만으로 답변에 필요한 근거를 이해할 수 있는지**를 함께 봐야 합니다.

## 1. 대표 청킹 전략 비교

| 전략 | 어디서 자르는가 | 적합한 문서·상황 | 주의점 |
|---|---|---|---|
| **고정 길이** | 일정한 문자 수 또는 토큰 수마다 자름 | 구조가 없는 텍스트, 성능 비교용 기준선 | 문장이나 조건과 예외가 중간에서 갈라질 수 있음 |
| **재귀적 분할** | 문단 같은 큰 단위부터 시도하고, 너무 길면 줄바꿈·문장 경계·공백 등 더 작은 단위로 분할 | 일반 텍스트, 구조 추출이 어려운 문서 | 구분자 설정에 따라 문장이나 목록이 갈라질 수 있음 |
| **문서 구조 기반** | 제목, 절, 조항, 표, 코드 블록 등 문서 구조를 기준으로 분할 | Markdown, HTML, 매뉴얼, 정책 문서 | 긴 절은 내부에서 추가로 나누고, 작은 절에는 제목 경로를 붙이는 편이 좋음 |
| **의미 기반** | 인접한 문장 묶음의 의미 유사도를 비교해 주제가 바뀌는 지점에서 분할 | 제목 없이 여러 주제가 이어지는 보고서, 상담 기록 | 문장 임베딩 계산이 추가되고, 분할 기준에 따라 청크 크기가 달라짐 |
| **부모–자식 방식** | 작은 자식 청크를 검색하고, 연결된 큰 부모 청크를 답변에 사용 | 세부 문구로 검색하되 앞뒤 설명이나 예외 조건이 필요한 규정·매뉴얼 | 여러 자식이 같은 부모를 가리킬 때 중복 제거가 필요하고, 부모가 길면 답변에 쓰는 토큰이 늘어남 |

실무에서는 전략을 조합할 수 있습니다. 예를 들어 매뉴얼을 **제목 기준으로 먼저 나누고, 긴 절만 재귀적으로 분할**할 수 있습니다. 부모–자식 방식도 이렇게 만든 청크에 적용할 수 있는 검색 설계입니다. [Microsoft Learn](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents?utm_source=chatgpt.com)

## 2. 청크 크기와 오버랩 정하기

**처음에는 `512토큰 / 오버랩 128토큰`을 기준으로 실험**할 수 있습니다. Microsoft의 Azure AI Search 문서에서 제시하는 시작 설정입니다. 실제 크기는 문서 구조, 질문 유형, 임베딩 모델에 맞춰 조정합니다. 한국어 문서도 사용할 임베딩 모델의 토크나이저로 길이를 확인하는 편이 정확합니다. [Microsoft Learn](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents?utm_source=chatgpt.com)

| 검색 결과에서 보이는 현상 | 먼저 조정할 것 |
|---|---|
| 원하는 문구가 검색되지만 조건이나 예외가 빠짐 | 관련 문단을 한 청크로 묶거나 부모 청크를 함께 가져오기 |
| 청크 하나에 여러 주제가 섞여 검색 결과가 모호함 | 청크를 줄이거나 소제목을 기준으로 나누기 |
| 답변 근거가 청크 경계에서 반복해서 끊김 | 문장·문단 경계로 옮기고, 필요한 구간에 오버랩 적용 |
| 검색 상위 결과가 거의 같은 내용으로 채워짐 | 오버랩을 줄이거나 검색 결과에서 유사 청크 중복 제거 |

**오버랩(Overlap)**은 앞 청크의 끝부분을 다음 청크의 시작에 다시 넣는 방식입니다. 경계에서 문맥이 끊기는 문제를 줄일 수 있지만, 오버랩이 커질수록 반복 저장되는 텍스트와 검색 결과의 중복이 늘어납니다. FAQ처럼 질문과 답변이 이미 한 단위로 묶여 있다면 오버랩 없이 시작할 수 있습니다. [Microsoft Learn](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents?utm_source=chatgpt.com)

## 3. 문서 유형별로 어디까지 묶을까?

| 문서 유형 | 권장 청킹 단위 | 함께 보존할 정보 |
|---|---|---|
| **FAQ** | 질문과 답변 한 쌍 | 서비스명, 카테고리 |
| **PDF 정책·지원 안내서** | 사업별 소제목 또는 조항. 지원 대상과 예외 조건은 가능하면 같은 청크에 배치 | 문서명, 사업명, 원본 페이지 |
| **Markdown·HTML 매뉴얼** | 제목별 섹션. 긴 섹션만 문단 단위로 추가 분할 | 상위 제목 경로, 원본 URL |
| **표가 많은 문서** | 작은 표는 전체, 큰 표는 관련 행 묶음 | 표 제목, 열 이름, 단위, 적용 기간 |
| **소스 코드** | 함수·클래스·메서드 | 파일 경로, 함수명, 관련 설명 |

예를 들어 지원 안내서에서 **“둘째 아이도 지원 대상인가요?”**라는 질문이 들어온다고 가정해 보겠습니다. `지원 대상`과 `예외 조건`이 서로 다른 청크에 들어가면 지원 대상만 검색될 수 있습니다. 두 문단을 함께 묶거나, 개별 청크를 검색한 뒤 **사업 전체를 담은 부모 청크**를 가져오면 두 근거를 함께 확인할 수 있습니다. 또 `출산지원금 > 지원 대상`처럼 **제목 경로를 임베딩할 텍스트에 포함**하면, 여러 사업에 반복되는 `지원 대상`이라는 소제목을 구분하는 데 도움이 됩니다. [Microsoft Learn](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents?utm_source=chatgpt.com)

## 4. 어떤 전략이 더 나은지 확인하는 방법

같은 문서에 **고정 길이 분할**과 **구조 기반 분할**을 각각 적용하고, 같은 임베딩 모델과 검색 설정으로 비교합니다. 평가 질문에는 단순 사실뿐 아니라 **예외 조건, 표의 수치, 앞뒤 문단을 함께 봐야 하는 질문**도 포함합니다.

1. **근거 검색률**을 확인합니다. 검색 상위 5개 안에 필요한 근거가 들어오는지 봅니다.
2. **근거의 완전성**을 확인합니다. 답에 필요한 대상·기간·예외가 모두 검색됐는지 봅니다.
3. **최종 답변**을 확인합니다. 검색된 근거에 맞게 답하고, 올바른 문서와 페이지를 인용하는지 봅니다.

입문 실습에서는 **제목·문단 기준으로 나누고, 긴 구간만 추가 분할하는 방식**부터 적용하기 좋습니다. PDF라면 청킹 전에 표의 열 순서와 문단의 읽기 순서가 올바르게 추출됐는지 확인하세요. 추출 단계에서 섞인 문맥은 청크 크기를 조절해도 복구하기 어렵습니다.
