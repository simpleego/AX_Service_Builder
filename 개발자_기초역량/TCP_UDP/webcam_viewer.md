# UDP 웹캠 실시간 영상 송신 예제

강사 PC의 웹캠 영상을 수강생들이 실시간으로 보는 프로그램입니다.
**UDP가 어떤 상황에 어울리는지**를 보여주는 것이 목적이라서 코드를 최대한 단순하게 만들었습니다.

| 파일 | 역할 |
|---|---|
| `udp_webcam_server.py` | 강사: 웹캠 촬영 → JPEG 압축 → 수강생에게 UDP로 송신 |
| `udp_webcam_client.py` | 수강생: UDP로 받은 JPEG → 이미지 복원 → 화면 표시 |

---

## 1. 실행 방법

### 준비

```
pip install opencv-python
```

### 실행

```
python udp_webcam_server.py              # 강사 PC (웹캠 필요)

```

- 다른 PC에서 접속이 안 되면 강사 PC의 **Windows 방화벽에서 UDP 6000 포트**를 허용하세요.

## 2. 왜 영상에는 UDP인가?

사진 파일 전송과 실시간 영상은 성격이 다릅니다.

| | 사진 파일 전송 | 실시간 영상 |
|---|---|---|
| 데이터 한 조각이 빠지면 | 파일이 깨짐 → **안 됨** | 화면이 한 번 튐 → **괜찮음** |
| 늦게 도착한 데이터는 | 기다려서라도 받아야 함 | 이미 지난 장면 → **쓸모없음** |
| 중요한 것 | 정확성 | **지연 없음 (실시간성)** |
| 어울리는 프로토콜 | TCP | **UDP** |

TCP로 영상을 보내면 패킷 하나가 유실됐을 때 **재전송될 때까지 뒤 프레임이 모두 멈춰서 기다립니다**.
화면이 멈췄다가 밀린 프레임이 한꺼번에 재생됩니다.
UDP는 빠진 프레임을 그냥 건너뛰고 **가장 최신 화면**을 보여줍니다.

> 실제로 화상회의, 인터넷 방송, 온라인 게임, 인터넷 전화는 UDP 기반 프로토콜(RTP, WebRTC, QUIC 등)을 씁니다.

## 3. 동작 구조

```
   수강생 A                  강사 (서버, UDP 6000)                 수강생 B
      |                              |                              |
      |------- "JOIN" -------------->|  viewers 목록에 A 추가        |
      |                              |<------------- "JOIN" --------|  B 추가
      |                              |                              |
      |                     [웹캠 1프레임 촬영]                       |
      |                     [640x480, JPEG 압축]                     |
      |<====== 프레임 #1 =============|============= 프레임 #1 =====>|
      |<====== 프레임 #2 =============|====== 프레임 #2 ===X (유실)   |  B는 #2를 못 봄
      |<====== 프레임 #3 =============|============= 프레임 #3 =====>|  #3부터 계속 보임
      |                              |                              |
      |------- "LEAVE" ------------->|  목록에서 A 제거               |
```

핵심 규칙은 두 가지뿐입니다.

1. **프레임 1장 = UDP 패킷 1개**
2. 서버는 **보내기만 하고 확인하지 않음**. ACK도, 재전송도 없습니다.

## 4. 코드 핵심 설명

### 4-1. UDP 소켓 만들기: `SOCK_DGRAM`

```python
sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
```

TCP 예제(`SOCK_STREAM`)와 비교하면 **`listen()`, `accept()`, `connect()`가 없습니다**.
UDP에는 "연결"이라는 개념이 없고, 패킷마다 받는 주소를 붙여서 보냅니다.

| TCP | UDP |
|---|---|
| `connect()` 후 `send(data)` | `sendto(data, 주소)` |
| `recv()` | `recvfrom()` → `(데이터, 보낸사람주소)` |
| 연결된 소켓 = 상대 1명 | 소켓 1개로 여러 명과 주고받음 |

### 4-2. 수강생 등록: 연결이 없으니 주소를 직접 기억한다

```python
viewers = set()                     # 수강생 주소 목록
data, addr = sock.recvfrom(1024)
if data == b"JOIN":
    viewers.add(addr)
```

TCP는 `accept()`가 연결을 만들어주지만, UDP 서버는 **누가 받을지를 직접 관리**해야 합니다.
수강생이 먼저 `JOIN` 패킷을 보내면, 서버는 `recvfrom()`이 알려주는 보낸 사람 주소를 저장해 둡니다.

`setblocking(False)`는 JOIN을 기다리느라 영상 송신이 멈추지 않도록 **들어온 패킷만 확인하고 바로 넘어가게** 하는 설정입니다.

### 4-3. 64KB 제한: 프레임을 패킷 하나에 넣기

```python
frame = cv2.resize(frame, (640, 480))
ok, jpg = cv2.imencode(".jpg", frame, [cv2.IMWRITE_JPEG_QUALITY, 50])
data = jpg.tobytes()

if len(data) <= MAX_PACKET:          # 65000 바이트 이하일 때만
    for viewer in viewers:
        sock.sendto(data, viewer)
```

UDP 패킷 하나는 **최대 약 64KB(65,507바이트)** 까지만 담을 수 있습니다.
원본 웹캠 프레임(640×480×3 = 약 900KB)은 너무 크기 때문에 **JPEG로 압축해서 보통 10~40KB**로 줄입니다.
그래도 너무 크면 그 프레임은 **보내지 않고 버립니다**. 영상이라서 한 장쯤 빠져도 괜찮습니다.

### 4-4. 수신: 깨지면 버리고, 안 오면 다시 요청

```python
try:
    data, _ = sock.recvfrom(65536)
except (socket.timeout, ConnectionResetError):
    sock.sendto(b"JOIN", SERVER)    # 1초간 안 오면 다시 등록 요청
    continue

frame = cv2.imdecode(np.frombuffer(data, np.uint8), cv2.IMREAD_COLOR)
if frame is None:                   # 복원 실패 → 버리고 다음 프레임
    continue
```

- **JOIN 패킷도 유실될 수 있습니다.** 그래서 1초 동안 영상이 안 오면 JOIN을 다시 보냅니다.
  서버를 나중에 켜도 클라이언트가 알아서 붙는 것도 이 덕분입니다.
- 받은 데이터가 정상 JPEG가 아니면 그냥 버립니다. 재전송을 요청하지 않습니다.

> `ConnectionResetError`: Windows에서는 받을 프로그램이 없는 주소로 UDP를 보내면,
> 다음 `recvfrom()`에서 이 에러가 납니다. UDP라서 실제로 연결이 끊긴 것은 아니니 무시하면 됩니다.

## 5. TCP 버전과 비교하면?

| 항목 | 이 예제 (UDP) | TCP로 만든다면 |
|---|---|---|
| 프레임 경계 | 패킷 = 프레임이라 자동으로 구분됨 | 스트림이라 "길이 + 데이터" 같은 구분 규칙 필요 |
| 네트워크가 나쁠 때 | 화면이 끊기듯 튐, **지연은 없음** | 화면이 멈췄다가 밀려서 재생, **지연 누적** |
| 수강생 관리 | 주소 목록을 직접 관리 | 연결(소켓)마다 스레드 |
| 수강생 프로그램이 꺼지면 | 서버는 모르고 계속 보냄 (LEAVE가 없으면) | 연결이 끊겨 서버가 바로 앎 |

## 6. 이 예제의 한계 (일부러 단순하게 만든 부분)

- **프레임 크기 64KB 제한**: 고화질(1080p)은 패킷 하나에 안 들어갑니다.
  실제 서비스는 프레임을 여러 조각으로 나누고 번호를 붙여서 보냅니다.
- **순서 보장 없음**: 늦게 도착한 옛 프레임이 최신 프레임 뒤에 표시될 수 있습니다. 같은 PC나 LAN에서는 거의 일어나지 않습니다.
- **비정상 종료한 수강생**: `q`로 닫지 않고 창을 강제로 끄면 LEAVE가 안 가서, 서버는 계속 보냅니다.
- **보안 없음**: 누구나 JOIN만 보내면 영상을 받을 수 있습니다.
