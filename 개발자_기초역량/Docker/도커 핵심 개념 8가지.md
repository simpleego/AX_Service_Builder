# 도커 핵심 개념 8가지

React 화면, FastAPI 서버, MariaDB 데이터베이스로 구성된 서비스에 도커를 적용한다고 생각하면 각 용어의 역할을 쉽게 구분할 수 있습니다.

| 용어 | 쉬운 설명 | 풀스택 예시 |
|---|---|---|
| **Dockerfile** | **이미지를 만드는 설명서**입니다. 어떤 기본 이미지에서 시작할지, 어떤 파일을 복사하고 라이브러리를 설치할지, 컨테이너를 시작할 때 기본으로 어떤 명령을 실행할지 적습니다. | Python 기본 이미지에 FastAPI 코드와 라이브러리를 넣고, 시작할 때 Uvicorn을 실행하도록 적습니다. |
| **Docker Image** | **앱과 앱 실행에 필요한 파일을 묶은 패키지**입니다. 같은 이미지로 여러 컨테이너를 만들 수 있고, `v1`, `v2` 같은 태그로 버전을 구분할 수 있습니다. | FastAPI 코드와 Python 실행 환경이 들어 있는 `my-api:v1` 이미지를 만듭니다. |
| **Docker Container** | **이미지로 만든 독립된 실행 환경**입니다. 시작하면 그 안에서 앱이 실행되고, 중지한 뒤 다시 시작할 수도 있습니다. | `my-api:v1` 이미지로 컨테이너를 시작하면 그 안에서 FastAPI 서버가 실행됩니다. |
| **Docker Registry** | **이미지를 올리고 내려받는 저장소 서비스**입니다. Docker Hub가 대표적이며, 팀 전용 비공개 레지스트리도 운영할 수 있습니다. | 개발자가 `my-api:v1`을 올려두면 배포 서버가 같은 이미지를 내려받아 실행합니다. |
| **Docker Volume** | **데이터를 컨테이너와 별도로 보관하는 공간**입니다. 볼륨을 유지하면 컨테이너를 삭제하고 새로 만들어도 데이터를 다시 연결해 사용할 수 있습니다. 필요하면 여러 컨테이너에 같은 볼륨을 연결할 수도 있습니다. | MariaDB의 데이터 파일을 볼륨에 저장하면 DB 컨테이너를 교체해도 회원과 주문 데이터가 남습니다. |
| **Docker Network** | **컨테이너들이 서로 통신하는 가상 네트워크**입니다. 어떤 컨테이너를 같은 네트워크에 연결할지 정할 수 있습니다. 호스트 PC에서 컨테이너의 서비스에 접속할 수 있도록 포트를 공개할 수도 있습니다. | 같은 네트워크에서 FastAPI가 `db:3306`으로 MariaDB에 접속하고, 개발자는 공개된 포트로 FastAPI에 접속합니다. |
| **Docker Compose** | **여러 컨테이너와 연결 설정을 한 파일에 정의하고 함께 실행하는 도구**입니다. 서비스별 이미지, 포트, 볼륨, 네트워크 등을 `compose.yaml`에 적습니다. | React, FastAPI, MariaDB를 정의해 두고 `docker compose up -d`로 한꺼번에 시작합니다. |
| **Docker CLI** | **터미널에서 도커를 조작하는 명령어 도구**입니다. 이미지 만들기, 컨테이너 실행, 실행 상태 확인 등을 할 수 있습니다. | `docker build`로 이미지를 만들고, `docker run`으로 컨테이너를 시작하고, `docker ps`로 실행 중인 컨테이너를 확인합니다. |

### 처음에는 세 가지부터 구분하면 됩니다

1. **Dockerfile을 작성합니다.** FastAPI 앱을 어떤 환경에서 어떻게 실행할지 적습니다.
2. **이미지를 빌드합니다.** Dockerfile의 지시에 따라 앱과 실행 환경을 하나로 묶습니다.
3. **컨테이너를 시작합니다.** 이미지를 바탕으로 실행 환경을 만들고 그 안에서 FastAPI 서버를 띄웁니다.

풀스택 프로젝트에서는 여기에 **네트워크**로 FastAPI와 MariaDB를 연결하고, **볼륨**에 DB 데이터를 보관합니다. 이 구성을 **Compose**에 적어두면 팀원도 같은 명령으로 실습 환경을 시작할 수 있습니다.

# Docker 핵심 개념 8가지 추가본

먼저 전체를 한 줄로 보면 이렇습니다. **Dockerfile**(레시피)로 **Image**(밀키트)를 만들고, 그 이미지로 **Container**(완성된 요리)를 실행합니다.

```
Dockerfile ──build──▶ Image ──run──▶ Container
                        ▲  │
                   pull │  │ push
                        │  ▼
                     Registry (Docker Hub)
```

---

### 1. Docker Engine: 컨테이너를 돌리는 엔진
- 사용자가 입력하는 **docker CLI**(클라이언트)와, 실제로 일을 하는 **dockerd**(데몬)로 나뉩니다.
- `docker run`을 입력하면 CLI가 데몬에게 요청을 보내고, 데몬이 컨테이너를 실행합니다.
- 우리 환경에서는 **VirtualBox의 Ubuntu VM 안에서** 엔진이 돌아갑니다.

### 2. Image: 실행 환경을 통째로 담은 템플릿
- OS 라이브러리, 런타임, 코드, 설정을 하나로 묶은 **읽기 전용** 패키지입니다.
- **비유**: 붕어빵 **틀**. 이미지 하나로 컨테이너를 여러 개 찍어낼 수 있습니다.
- 이미지는 **레이어**로 쌓여 있어서, 같은 레이어는 재사용되고 다운로드도 빠릅니다.
- 이름 형식은 `이름:태그`입니다. 예: `nginx:alpine`, `python:3.12`

### 3. Container: 이미지를 실행한 것
- 이미지 위에 쓰기 가능한 층을 얹어 실행한 **격리된 프로세스**입니다.
- **비유**: 틀에서 찍어낸 **붕어빵**.
- VM과 달리 OS 전체를 띄우지 않고 호스트 커널을 함께 씁니다. 그래서 **몇 초 안에 시작**되고 가볍습니다.
- 컨테이너를 삭제하면 그 안에서 바뀐 내용도 함께 사라집니다. 데이터를 남기려면 Volume을 써야 합니다.

| | VM | 컨테이너 |
|---|---|---|
| 포함 범위 | OS 전체 | 앱과 라이브러리만 |
| 시작 시간 | 수십 초~수 분 | 1~2초 |
| 크기 | GB 단위 | MB 단위 |

### 4. Dockerfile: 이미지를 만드는 레시피
```dockerfile
FROM python:3.12-slim        # 기반 이미지
WORKDIR /app                 # 작업 폴더
COPY requirements.txt .
RUN pip install -r requirements.txt   # 빌드할 때 실행
COPY . .
EXPOSE 8000                  # 사용할 포트 표시
CMD ["python", "app.py"]     # 컨테이너가 시작될 때 실행
```
- `docker build -t myapp:1.0 .` 명령으로 이 레시피에서 이미지를 만듭니다.
- **"내 PC에서는 되는데…"** 문제를 없애 줍니다. 누가 빌드해도 같은 환경이 나옵니다.

### 5. Registry: 이미지 저장소
- 이미지를 올리고(push) 내려받는(pull) 곳입니다. **비유**: 코드의 GitHub, 앱의 앱스토어.
- 대표적인 곳은 **Docker Hub**이고, 그 밖에 GHCR, AWS ECR, 사내 Harbor 등이 있습니다.
- 명령어: `docker pull nginx`, `docker push 계정/myapp:1.0`

### 6. Volume: 데이터 영구 저장
- 컨테이너는 삭제되면 데이터도 함께 사라집니다. 그래서 데이터는 **컨테이너 바깥**에 저장해야 합니다.
- **Named Volume**: Docker가 관리하는 저장소입니다. DB 데이터 저장에 권장합니다.
  `docker run -v pgdata:/var/lib/postgresql/data postgres`
- **Bind Mount**: 호스트 폴더를 그대로 연결합니다. 개발 중 코드를 실시간으로 반영할 때 씁니다.
  `docker run -v $(pwd):/app ...`

### 7. Network: 컨테이너 간 통신과 외부 노출
- **포트 매핑**(`-p 호스트:컨테이너`)으로 외부에서 컨테이너에 접속할 수 있게 합니다.
  `docker run -p 80:80 nginx`를 실행하면 우리 환경에서는 Windows의 `localhost:8080`, VM의 80번 포트, 컨테이너의 80번 포트 순서로 연결됩니다.
- 같은 사용자 정의 네트워크에 있는 컨테이너끼리는 **컨테이너 이름으로** 서로를 부를 수 있습니다. 예: 앱에서 `db:5432`로 접속
- 주요 드라이버: `bridge`(기본), `host`, `none`

### 8. Docker Compose: 여러 컨테이너를 한 번에 관리
- 웹, DB, 캐시처럼 여러 컨테이너를 **YAML 파일 하나로** 정의하고 함께 실행합니다.
```yaml
services:
  web:
    build: .
    ports: ["8000:8000"]
    depends_on: [db]
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: example
    volumes: [pgdata:/var/lib/postgresql/data]
volumes:
  pgdata:
```
- `docker compose up -d`로 전체를 실행하고, `docker compose down`으로 전체를 정리합니다.
- 네트워크가 자동으로 만들어져서 `web`이 `db`라는 이름으로 DB에 접속할 수 있습니다.

## 한눈에 정리

| # | 개념 | 비유 | 핵심 명령어 |
|---|---|---|---|
| 1 | Engine | 주방 | `docker version` |
| 2 | Image | 붕어빵 틀 | `docker images`, `docker pull` |
| 3 | Container | 붕어빵 | `docker run`, `docker ps`, `docker rm` |
| 4 | Dockerfile | 레시피 | `docker build` |
| 5 | Registry | 앱스토어 | `docker push / pull` |
| 6 | Volume | 외장하드 | `docker volume ls` |
| 7 | Network | 내선 전화망 | `docker network ls`, `-p` |
| 8 | Compose | 오케스트라 지휘자 | `docker compose up / down` |

> 강의 순서로는 **Image/Container로 직접 실행 → Dockerfile로 빌드 → Volume/Network → Compose로 묶기 → Registry로 배포**의 흐름을 추천합니다.

원하시면 각 개념을 VM에서 바로 따라 할 수 있는 실습 예제(`work` 공유 폴더용)로 만들어 드리겠습니다.
