그림은 **FastAPI 애플리케이션에 HTTP 요청이 들어와 응답이 나가는 전체 흐름을 식당에 비유한 것**입니다. 다만 실제 서버에서는 그림의 `Nginx → Gunicorn → Uvicorn → FastAPI` 사이에 몇 가지 중요한 단계가 더 있습니다.

전체 흐름을 시간 순서대로 확장하면 다음과 같습니다.

```text
[사용자/브라우저]
     │
     │ ① HTTP/HTTPS 요청
     ▼
[DNS / TCP / TLS]
     │
     ▼
[Nginx]
리버스 프록시
     │
     │ ② 요청 전달
     ▼
[Gunicorn Master]
프로세스 관리자
     │
     │ ③ Worker 선택
     ▼
[Uvicorn Worker]
ASGI 서버
     │
     │ ④ ASGI 요청 생성
     ▼
[FastAPI]
     │
     ├─ ⑤ Middleware
     ├─ ⑥ Router
     ├─ ⑦ Pydantic 검증
     ├─ ⑧ Dependency
     ├─ ⑨ 비즈니스 로직
     │
     ├───────────────┐
     ▼               ▼
 [Database]       [외부 API / AI]
     │               │
     └───────┬───────┘
             │
             ▼
       ⑩ 결과 생성
             │
             ▼
       [FastAPI]
             │
       JSON 직렬화
             ▼
       [Uvicorn]
             │
       HTTP 응답
             ▼
       [Gunicorn]
             │
             ▼
        [Nginx]
             │
             ▼
     ⑪ 사용자 브라우저
```

## 1. 사용자가 식당에 요청한다 — Browser → Server

예를 들어 프론트엔드에서 다음 요청을 보냈다고 하겠습니다.

```javascript
fetch("https://example.com/api/products")
```

사용자가 실제로 전달하는 것은 개념적으로 이런 HTTP 요청입니다.

```http
GET /api/products HTTP/1.1
Host: example.com
```

식당으로 표현하면,

> "상품 목록 하나 주세요."

라는 주문을 보내는 것입니다.

이때 실제 네트워크에서는 먼저 도메인의 IP 주소를 찾는 DNS 과정이 있을 수 있고, HTTPS라면 TLS 연결도 이루어집니다.

---

# 2. Nginx — 식당 접수 담당자

그림에서 Nginx가 **Receptionist(접수 담당자)** 로 표현된 이유가 정확합니다.

Nginx는 일반적으로 애플리케이션의 맨 앞에서 요청을 받습니다.

```text
Internet
   ↓
Nginx
   ↓
Backend
```

예를 들어 사용자가

```text
https://example.com/api/products
```

로 요청하더라도 실제 FastAPI는 내부적으로

```text
127.0.0.1:8000
```

에서 실행되고 있을 수 있습니다.

Nginx 설정은 대략 다음과 같습니다.

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8000;
}
```

그래서

```text
사용자
   ↓
https://example.com/api/products
   ↓
Nginx
   ↓
http://127.0.0.1:8000/api/products
```

로 전달합니다.

### Nginx가 하는 대표적인 일

```text
요청 접수
보안/HTTPS 처리
리버스 프록시
정적 파일 전달
로드 밸런싱
압축
캐싱
접속 로그
```

식당으로 치면 손님이 **주방으로 직접 들어가지 못하도록 하는 프런트 데스크**입니다.

---

# 3. Gunicorn — 직원 관리자

다음 단계가 Gunicorn입니다.

여기서 가장 중요한 개념은

> **Gunicorn은 FastAPI의 기능을 수행하는 서버라기보다 여러 Worker 프로세스를 관리하는 관리자 역할을 한다**

는 것입니다.

예를 들어,

```text
Gunicorn Master
       │
 ┌─────┼─────┬─────┐
 ▼     ▼     ▼     ▼
W1    W2    W3    W4
```

처럼 여러 프로세스를 실행할 수 있습니다.

식당으로 보면 매니저가

```text
손님 주문 1 → 직원 A
손님 주문 2 → 직원 B
손님 주문 3 → 직원 C
```

처럼 일을 배분하는 것과 비슷합니다.

예를 들어 과거에 흔히 사용하던 형태는 이런 식입니다.

```bash
gunicorn main:app \
    -k uvicorn.workers.UvicornWorker \
    -w 4
```

여기서

```text
-w 4
```

는 Worker 4개를 의미합니다.

즉,

```text
Gunicorn
   ├─ Uvicorn Worker 1
   ├─ Uvicorn Worker 2
   ├─ Uvicorn Worker 3
   └─ Uvicorn Worker 4
```

와 같은 구조입니다.

---

# 4. Uvicorn — 실제 주문을 빠르게 운반하는 직원

그림에서 Uvicorn을 **High-speed sous chef**라고 표현했는데, 서버 구조에서는 조금 다르게 이해하는 것이 좋습니다.

Uvicorn은

> **ASGI 서버**

입니다.

FastAPI 자체는 네트워크에서 직접 HTTP 요청을 받는 프로그램이 아닙니다.

FastAPI는

```python
@app.get("/products")
def products():
    ...
```

같은 **애플리케이션 코드**를 정의할 뿐입니다.

실제 네트워크 연결은 Uvicorn이 처리합니다.

```text
HTTP 요청
   ↓
Uvicorn
   ↓
ASGI
   ↓
FastAPI
```

그래서 개발할 때 다음 명령을 실행합니다.

```bash
uvicorn main:app --reload
```

의미는

```text
main.py
  ↓
app 객체
  ↓
Uvicorn이 실행
```

입니다.

---

# 5. Uvicorn이 HTTP를 ASGI 형태로 변환

여기가 FastAPI 구조를 이해할 때 매우 중요한 부분입니다.

브라우저는 HTTP를 사용합니다.

```http
GET /products
```

하지만 FastAPI 내부에서는 이를 **ASGI 규격**으로 처리합니다.

개념적으로는 다음과 같은 정보가 전달됩니다.

```python
{
    "type": "http",
    "method": "GET",
    "path": "/products",
    ...
}
```

즉 Uvicorn이 중간에서

```text
HTTP 세계
   ↓
ASGI 세계
   ↓
FastAPI
```

를 연결해 줍니다.

그래서 정확하게 말하면

```text
Uvicorn = HTTP Server + ASGI Server
```

라고 이해하면 좋습니다.

---

# 6. FastAPI에 요청 도착

이제 그림의 **Head Chef**, 즉 주방장 FastAPI에게 주문이 전달됩니다.

예를 들어,

```python
@app.get("/products")
def get_products():
    return {"products": ["노트북", "키보드"]}
```

요청

```http
GET /products
```

이 들어오면 FastAPI가 URL을 보고 어떤 함수를 실행해야 하는지 찾습니다.

```text
GET /products
      ↓
@app.get("/products")
      ↓
get_products()
```

이를 **Routing**이라고 합니다.

---

# 7. Middleware 처리

그림에는 빠져 있지만 실제 FastAPI에서 상당히 중요한 단계입니다.

FastAPI 함수가 실행되기 전에 Middleware가 동작할 수 있습니다.

예를 들어,

```text
요청
 ↓
CORS Middleware
 ↓
인증 Middleware
 ↓
로그 Middleware
 ↓
FastAPI Router
```

현재 자주 사용하신 코드도 바로 Middleware입니다.

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],
    allow_methods=["*"],
    allow_headers=["*"],
)
```

즉 식당으로 비유하면 주방에 주문이 들어가기 전에

```text
예약 확인
회원 확인
출입 확인
주문표 확인
```

을 하는 단계라고 볼 수 있습니다.

---

# 8. FastAPI가 입력 데이터를 검증

FastAPI의 중요한 특징이 여기에서 등장합니다.

예를 들어 프론트에서

```json
{
    "num1": 10,
    "num2": 20
}
```

을 보냅니다.

FastAPI 코드가

```python
class CalcData(BaseModel):
    num1: int
    num2: int
```

라면 FastAPI/Pydantic이 먼저 검사합니다.

```text
num1 존재?
  ↓
정수인가?

num2 존재?
  ↓
정수인가?
```

정상이라면

```text
10 + 20
```

을 수행합니다.

잘못 보내면

```json
{
    "num1": "hello",
    "num2": 20
}
```

애플리케이션 함수까지 정상적으로 들어가기 전에 validation error가 발생할 수 있습니다.

식당으로 비유하면

> 주문서에 필요한 내용이 제대로 작성되었는지 확인하는 과정

입니다.

---

# 9. Dependency 처리

FastAPI에서 매우 중요한 기능 중 하나입니다.

예를 들어,

```python
def get_db():
    ...
```

```python
@app.get("/products")
def products(db = Depends(get_db)):
    ...
```

라고 한다면 FastAPI는 함수 실행 전에 필요한 객체를 준비합니다.

```text
제품 목록 요청
       ↓
DB 연결 필요
       ↓
get_db()
       ↓
DB Session 생성
       ↓
products()
```

여기에 인증도 포함될 수 있습니다.

```text
요청
 ↓
토큰 확인
 ↓
로그인 사용자 확인
 ↓
DB 연결
 ↓
API 함수 실행
```

# 10. 실제 비즈니스 로직 수행

이제 주방장이 실제 요리를 시작합니다.

예를 들어,

```python
@app.get("/products")
def get_products():
    products = db.query(Product).all()
    return products
```

라면

```text
FastAPI
   ↓
Service
   ↓
Repository
   ↓
PostgreSQL
```

같은 구조가 될 수도 있습니다.

조금 더 큰 프로젝트에서는 보통

```text
Router
   ↓
Service
   ↓
Repository
   ↓
Database
```

처럼 분리합니다.

예를 들어:

```text
product_router.py
        ↓
product_service.py
        ↓
product_repository.py
        ↓
PostgreSQL
```

# 11. DB나 AI 서버에 요청

현재의 AX 애플리케이션이라면 여기서 한 단계가 더 중요합니다.

FastAPI가 직접 모든 일을 하는 것이 아니라 외부 서비스를 호출할 수 있습니다.

```text
FastAPI
 ├─ PostgreSQL
 ├─ Redis
 ├─ OpenAI API
 ├─ Gemini
 ├─ Hugging Face
 └─ Vector DB
```

예를 들어 RAG라면,

```text
FastAPI
   ↓
사용자 질문
   ↓
Embedding
   ↓
Vector DB 검색
   ↓
관련 문서 검색
   ↓
LLM 호출
   ↓
답변 생성
```

이 과정까지 모두 끝나야 최종 HTTP 응답이 만들어집니다.

# 12. FastAPI가 Python 객체를 응답으로 변환

예를 들어 함수가

```python
return {
    "name": "홍길동",
    "score": 90
}
```

을 반환했다고 하겠습니다.

Python에서는

```python
dict
```

입니다.

하지만 브라우저에 보낼 때는 보통 JSON 형태가 됩니다.

```json
{
    "name": "홍길동",
    "score": 90
}
```

즉,

```text
Python 객체
    ↓
Serialization
    ↓
JSON
```

과정이 발생합니다.

# 13. Uvicorn이 HTTP Response 생성

FastAPI가 만든 결과는 다시 Uvicorn으로 넘어갑니다.

```text
FastAPI

{"result": 30}

     ↓

Uvicorn
```

Uvicorn은 이를 HTTP 응답으로 전달합니다.

개념적으로

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"result":30}
```

와 같은 형태가 됩니다.

---

# 14. Gunicorn을 거쳐 Nginx로 반환

응답 경로는 요청과 반대 방향입니다.

```text
FastAPI
   ↓
Uvicorn
   ↓
Gunicorn 관리 하의 Worker
   ↓
Nginx
   ↓
Internet
```

여기서 그림의 마지막 **200 OK Response Plate**가 등장합니다.

`200 OK`는 요리 이름이 아니라 HTTP 상태 코드입니다.

```text
200 → 성공
201 → 생성 성공
400 → 잘못된 요청
401 → 인증 필요
403 → 권한 없음
404 → 데이터 없음
422 → 입력 데이터 검증 오류
500 → 서버 오류
```

# 15. JavaScript가 응답을 받음

처음 요청했던 프론트엔드가 응답을 받습니다.

```javascript
const response =
    await fetch("http://localhost:8000/add?num1=10&num2=20");

const data =
    await response.json();

console.log(data);
```

서버가

```json
{
    "합계": 30
}
```

을 반환하면 JavaScript가 이를 객체로 변환합니다.

```javascript
data["합계"]
```

결과:

```text
30
```

그리고 DOM에 표시합니다.

```javascript
document.querySelector("#result").textContent =
    data["합계"];
```

화면에는

```text
결과 : 30
```

이 나타납니다.

# 전체를 시간 흐름으로 다시 압축하면

수업에서는 다음 **12단계**로 설명하면 가장 이해하기 좋습니다.

```text
① 사용자
   "상품 주세요"
       │
       ▼
② Browser / JavaScript
   fetch()
       │
       ▼
③ HTTP/HTTPS
       │
       ▼
④ Nginx
   요청 접수 / Proxy
       │
       ▼
⑤ Gunicorn
   Worker 프로세스 관리
       │
       ▼
⑥ Uvicorn Worker
   HTTP → ASGI
       │
       ▼
⑦ FastAPI Middleware
   CORS / 인증 / 로그
       │
       ▼
⑧ FastAPI Router
   URL → 함수 연결
       │
       ▼
⑨ Pydantic / Dependency
   데이터 검증 / DB 연결
       │
       ▼
⑩ Business Logic
   DB / AI / 외부 API
       │
       ▼
⑪ FastAPI → Uvicorn → Nginx
   JSON + HTTP Response
       │
       ▼
⑫ Browser
   JS가 JSON을 받아 DOM 변경
```

## 식당 비유를 조금 더 정확하게 확장하면

| 실제 기술          | 식당 비유    | 역할               |
| -------------- | -------- | ---------------- |
| Browser        | 손님       | 주문               |
| HTTP           | 주문 전달 방법 | 주문서 규칙           |
| Nginx          | 안내/접수 직원 | 손님 접수            |
| Gunicorn       | 직원 관리자   | Worker 관리        |
| Uvicorn        | 주문 전달 직원 | HTTP와 FastAPI 연결 |
| FastAPI Router | 주문 분류 담당 | 담당 함수 선택         |
| Pydantic       | 주문서 검사   | 입력 검증            |
| Dependency     | 재료/도구 준비 | DB, 인증 등 준비      |
| Service        | 주방장/조리법  | 업무 로직            |
| PostgreSQL     | 식재료 창고   | 데이터 저장           |
| AI/LLM         | 전문 조리 파트 | AI 처리            |
| JSON           | 완성된 요리   | 결과 데이터           |
| HTTP 200       | 정상 배식 표시 | 성공 응답            |

그리고 그림에서 한 가지는 **조금 수정해서 이해하는 것이 좋습니다.**

```text
Gunicorn
   ↓
Uvicorn
   ↓
FastAPI
```

를 완전히 서로 독립된 세 서버가 순차적으로 데이터를 넘긴다고 생각하기보다는,

```text
Gunicorn Master
      │
      ├─ Uvicorn Worker
      │       └─ FastAPI App
      │
      ├─ Uvicorn Worker
      │       └─ FastAPI App
      │
      └─ Uvicorn Worker
              └─ FastAPI App
```

처럼 이해하는 편이 실제 구조에 가깝습니다.

즉 **Gunicorn이 Uvicorn Worker 여러 개를 관리하고, 각 Uvicorn Worker 안에서 FastAPI 애플리케이션이 실행되는 구조**입니다.

그리고 개발 단계에서는 굳이 전체를 사용하지 않고 보통

```text
브라우저
   ↓
Uvicorn
   ↓
FastAPI
```

만으로 충분합니다.

배포 환경으로 가면서

```text
Internet
   ↓
Nginx
   ↓
프로세스 관리
   ↓
Uvicorn Worker
   ↓
FastAPI
   ↓
PostgreSQL / AI
```

처럼 확장한다고 가르치면 비전공자도 **“왜 개발할 때는 `uvicorn main:app --reload` 하나만 썼는데, 배포할 때 Nginx 같은 것이 추가되는가”**를 자연스럽게 이해할 수 있습니다.
